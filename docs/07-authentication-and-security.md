# 認証・セキュリティ

## 基本方針

Firebase Authentication をログイン認証に利用します。

管理者権限は検証済みFirebase IDトークンの`admin: true`または`role: "admin"`で判定します。
初期設定用の`FIREBASE_AUTH_ADMIN_EMAILS`を利用する場合は、メールアドレスの完全一致に加え、`email_verified === true`を必須にします。
メール許可リストのみで認可する場合、未確認・確認状態未設定のメールは許可リストに一致しても管理者APIへアクセスできません（403）。
メール確認後はIDトークンを再取得するか、ログインし直してください。
custom claimsによる既存の管理者判定は維持しています。claimsへの完全移行では、既存管理者へ権限を付与・確認してからメール許可リストを廃止します。

管理者・会員の共通認証処理は`verifyIdToken(token, true)`で失効・無効化を確認します。失効したトークンは401で拒否します。
アカウント削除では確認済みメールに加え、`auth_time`が直近5分以内であることをサーバーで検証します。IDトークンの更新時刻`iat`では代替できません。
削除画面で現在のパスワードを再入力し、Firebaseの`reauthenticateWithCredential`で本人確認後、更新したIDトークンを送ります。パスワードをアプリAPIやDBには送信・保存しません。
プロフィール保存前に登録が中断した場合も、同じ本人確認を経てFirebaseの認証ユーザーを削除できます。削除のために仮のプロフィールを作成する必要はありません。既存プロフィールの無効化後に認証ユーザーの削除が失敗した場合は、プロフィールを復元します。認証ユーザーが削除済みの場合は成功扱いとします。
メールアドレス変更の開始処理は既存の`verifyBeforeUpdateEmail`による再認証要件を維持します。

## 漏えい・権限解除時のセッション失効

運用担当者のみが利用するコマンドです。対象UIDとFirebaseプロジェクトを確認してから実行します。今回の実装・テストでは実ユーザーへ実行していません。
既に発行されたIDトークンの拒否には、この失効確認に対応した版を対象環境の全APIへ反映する必要があります。通常の検証だけを行う旧版では失効を検知できません。
既存の`.env.local`等のFirebase Admin認証情報を読み込みます。DB用の`APP_ENV`ではFirebaseの接続先は切り替わりません。

```powershell
# 漏えい時: 対象ユーザーのセッションを失効（管理者claimsは維持）
npm.cmd run auth:revoke -- --uid <UID> --confirm <UID> --project <FIREBASE_PROJECT_ID>

# 管理者権限解除: admin/role=adminのclaimsを除去し、既存セッションも失効
npm.cmd run auth:remove-admin -- --uid <UID> --confirm <UID> --project <FIREBASE_PROJECT_ID>
```

メール許可リストにも含まれる管理者は、先に全環境の許可リストから削除してアプリを再起動・再デプロイしてください。残っている場合、権限解除コマンドは実行を拒否します。
他のcustom claimsは保持します。セッション失効に失敗した場合は成功扱いにせずエラーになります。原因を解消して再実行してください。
漏えい時にはセッション失効だけでなく、アカウントの保護と原因調査も行います。これらのコマンドはユーザー一覧全体に対する一括処理を行いません。

Firebase公式: https://firebase.google.com/docs/auth/admin/manage-sessions

認証主体は `Account` とし、予約者情報とは分離します。

- Accountはログイン可能な利用者だけを保持します。
- 管理者代理予約・非会員予約ではAccountを作成しません。
- 予約者の氏名・メール・電話等はReservationのスナップショットです。
- メールアドレス一致だけでAccountと既存予約を紐付けません。
- 過去の管理者登録予約を後からAccountへ連携しません。
- マイページには `Reservation.account.firebaseUid == session.uid` の予約だけを表示します。

## 本人予約

ログイン済み利用者が予約する場合のみ、Firebase UIDからAccountを取得してReservation.accountへ設定します。

Accountが存在しない場合は、予約作成処理で曖昧なメール照合を行わず、Account登録フローを完了させてから予約します。

## 管理者代理予約

管理者が入力した予約者情報はReservationへ直接保存します。

- Account検索を行わない
- Accountを自動作成しない
- 既存Accountとメールが一致しても紐付けない

これにより、本人が登録していないのに会員情報が存在するように見える状態を避けます。

## 過去予約

Account作成時に過去予約の探索・自動紐付け・手動紐付けを行いません。

過去の代理予約・非会員予約への照会や変更は管理者が対応します。公開APIでメール・電話の一致による本人権限の付与は行いません。

## 削除処理と再作成防止（Drizzle構成）

Firebaseの削除前にUID単位の削除状態を `account_deletion` に記録します。プロフィール未保存のFirebaseユーザーも対象です。削除中の保存・本人予約・管理者復元は拒否し、完了後もUIDの削除記録を保持します。

Firebase削除が失敗した場合は、ユーザーがまだ存在することを確認できたときだけDBを復旧します。既にAuthから削除済みなら完了扱いにし、状態を確認できない場合は削除中のまま保持します。処理中の二重DELETEは409です。プロセス中断・状態不明の回復には管理者の確認が必要です。

旧Data Connect構成にはこの削除状態テーブルと同じトランザクション保証はありません。公開前の残課題は `13-system-review-2026-10-15.md` に記録しています。
