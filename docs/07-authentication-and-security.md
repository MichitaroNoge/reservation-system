# 認証・セキュリティ

## 認証方式

現行アプリにログイン機能は実装されていません。

画面上では `role` state により `admin` と `customer` を切り替えていますが、これは認証ではありません。

根拠: `const [role, setRole] = useState<"admin" | "customer">("admin")` in `app/page.tsx`。

## 権限の種類

現行コードで実装されている権限種別はありません。

画面上の便宜的な区分:

| 区分 | 実装状況 | 操作 |
| --- | --- | --- |
| 顧客 | 画面stateのみ | 予約申請 |
| 管理者 | 画面stateのみ | 予約、顧客、店舗、メニュー管理 |

## 権限ごとに実行可能な操作

実際の認可チェックがないため、APIを直接呼び出せば誰でも更新操作が可能な状態です。

## 個人情報の扱い

予約データには以下の個人情報が含まれます。

- 氏名
- メールアドレス
- 電話番号

現行では `data/reservation-db.json` に平文保存されます。このファイルは `.gitignore` によりGit管理から除外されています。

Seedやサンプルデータにはサンプルメール・電話番号が含まれています。

## 秘密情報の管理方法

- `.env.example` に環境変数名が定義されています。
- `.env*` は `.gitignore` で除外されています。ただし `.env.example` は除外対象外です。
- 設計資料では環境変数の値を記載しません。

根拠: `.env.example`, `.gitignore`。

## セキュリティ上の注意点

- 管理画面が認証なしで表示可能。
- APIが認証なしで更新可能。
- Data Connect定義がPUBLIC認可のプロトタイプ状態。
- API入力の検証が不足。
- ファイルDBの排他制御がないため、同時更新時の競合リスクがある。
- 顧客削除が関連予約削除を伴うため、誤操作時の影響が大きい。
- 例外ステータス変更の理由は永続化されないため、監査証跡が残らない。

## 現在確認できるリスク

| リスク | 影響 | 対応案 |
| --- | --- | --- |
| 認証なし | 誰でも管理操作可能 | Firebase Authentication等を導入 |
| 認可なし | 権限分離不可 | ロールベース認可をAPI側に実装 |
| APIバリデーション不足 | 不正データ混入 | Zod等で検証 |
| ファイルDB | 同時更新・永続性・バックアップ課題 | RDB移行または排他制御 |
| メール未実装 | 確認連絡の実送信ができない | メール基盤と送信ログ設計 |
| 監査ログなし | 誰が変更したか追跡不可 | 操作ログを保存 |
