# アカウントのログインメール重複防止と再有効化（2026-11-05）

## 変更した動作

- ログインメールは `trim().toLowerCase()` で統一。PostgreSQLの `normalize_login_email()` もECMAScriptと同じ前後空白を除去する。Gmail固有のドット・`+`の同一視はしない。
- `account_active_login_email_unique` は **active=true の行だけ** を対象とする部分一意インデックス。追加連絡先 `account_contact_email`、旧 `customer`、予約スナップショットは対象外。
- 新規作成・メール変更は、同じメールの有効アカウント、管理者による無効アカウント、削除処理中アカウントがあれば409。本人削除が完了した旧行だけはメールを再利用できる。
- 再有効化は元の行のactiveを更新する。別の有効アカウントと競合すれば409。削除記録があれば処理中・完了を問わず403。新しいDBアカウントやFirebaseユーザーは作らない。
- UIDロックで削除・プロフィール作成/更新・再有効化を排他制御し、メールロックで異なるUID間の作成・同期・再有効化を直列化する。最終的な有効メールの一意性はDBインデックスでも強制する。エラー時はトランザクションが更新とupdatedAtをロールバックする。
- 管理者による無効化はFirebaseユーザーを残す。本人削除は、削除開始記録と無効化を一括保存した後にFirebaseを削除し、最後に完了記録を残す。完了記録前は別UIDの再登録も拒否する。Firebaseが失敗し、ユーザーの存在を確認できた場合だけ元の状態を復旧する。結果不明時は削除中の保護を残す。
- 同じメールの再登録は新しいUID・新しいaccount IDを持つ。旧予約のaccount_id、予約時スナップショット、旧追加連絡先は変更せず、メールによる履歴の再関連付けもしない。Firebaseの旧UIDの権限はコピーしない。
- 管理画面は `lifecycleStatus`（disabled/deleting/deleted）と `reactivationBlockedReason` を受け取り、削除状態を名前・メールから推測しない。削除中・削除済みは有効化ボタンなし。既知の重複は無効ボタンと理由を表示。処理中は全有効化ボタンを止め、成功と対象行の失敗理由を表示する。管理者無効化直後のローカル表示にも状態を反映する。

## FirebaseとDBのメール

本人の初回プロフィール作成は、検証済みFirebase IDトークンのUIDとメールを入力元とする（既存どおり、メール確認前のプロフィール登録は可能）。プロフィール本文のcontactは使わない。

既存プロフィールのPOST/PATCHはDBのログインメールを保持する。古いトークンを持つプロフィール保存で、既に同期したメールを巻き戻さない。

メール変更は既存の `verifyBeforeUpdateEmail()` → 確認リンク → トークン更新 → `/api/accounts/me/email` の経路を維持する。同期時にはFirebase Admin `getUser()` の現在の確認済みメールとトークンを照合する。古いトークンは409で再ログインを案内する。DB更新には同じ重複チェックとインデックスを適用する。同期に失敗した場合、DBのメール・プロフィールは変更せず、変更通知も作らない。Firebase側の変更を自動で巻き戻す処理は追加していないため、競合があれば管理者による確認が必要。旧メールへの通知失敗は既存どおり成功レスポンス内のnotificationで区別する。

管理者向け `/api/accounts` と互換 `/api/customers` の作成も、既存Firebase UIDのメールと一致することをサーバーで照合する。存在しないUIDは404、不一致は409。Firebaseユーザーの代理作成はしない。

## 適用条件と移行手順（今回、実データには未適用）

1. **この機能を利用する環境は `DB_PROVIDER=drizzle` と既存0020までの物理スキーマが必要。** 旧Data Connectの生成SDKには、削除記録と必要なトランザクションがない。安全性を迂回しないよう、その経路のアカウント作成・プロフィール更新・メール同期・再有効化は503で停止する。本人削除も削除記録/トランザクション未対応なら503。旧Data Connectが既定の環境へ、この変更だけをそのままデプロイしない。プロバイダー移行は別途確認する。参照・既存予約・管理者無効化などは維持する。
2. バックアップと物理スキーマの照合後、読み取り専用の `scripts/sql/check-login-email-duplicates.sql` を実行する。有効メールの正規化値と、対象account ID・Firebase UID・元メールを返す。空結果が制約追加の前提。
3. 重複があれば対象とFirebase認証情報を運用担当者が確認する。**自動削除・自動統合・自動無効化は実装していない。** 予約の関連付けやスナップショットを移し替えない。どのアカウントのログインメールを正すか等を個別に判断し、再検査する。
4. `0021_account_login_email.sql` はトランザクション内でaccountテーブルの書き込みをロックし、重複を再検査してからインデックスを作る。事前検査後に重複が入っても安全に停止する。重複時は例外でマイグレーション全体をロールバックし、既存行は変更しない。書き込みを一時停止するため、保守時間帯と接続側のlock_timeoutを運用時に検討する。単独SQLを手動実行する場合もBEGIN/COMMITが必要。
5. 承認された環境で既存の移行手順に従って制約を適用してから、このアプリを使用する。ローカルの既存ツール `npm run db:migrate` は開発/テスト専用であり、本番には使えない。Cloud SQLの既存DBへ全履歴のマイグレーションを無条件に流さない。

マイグレーションは関数と部分一意インデックスを追加するだけで、保存済みメールの書き換え・アカウント修復はしない。無効な旧行と現行の有効行のメールが重複していても移行は可能で、再有効化だけが拒否される。削除履歴の移行不足をメールから補完してはいけない。
