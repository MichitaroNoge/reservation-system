# 問い合わせ機能の調査と実装計画（2026-10-19）

状態：2026-10-20に実装承認。実装結果は [38. 問い合わせ機能の実装記録](38-inquiry-implementation-2026-10-20.md) を参照。

## 確認済みの方針

- 一般問い合わせは未ログインでも受付可能。メールの確認リンクは挟まず、送信後にその場で問い合わせ番号を発行する（ユーザー回答）。
- WAF・ボット対策サービスの本番利用は未定（ユーザー回答）。外部サービスの契約・設定を今回独断では追加しない。
- 現行のローカルPostgreSQL / Drizzle構成を対象とし、クラウドDB移行は行わない。
- 予約問い合わせは、既存の認証・予約へのアクセス権限を使ってサーバーで関連付ける。

## 2. 推奨する構成

問い合わせのDB処理、入力検証、受付サービス、回答メールサービス、画面コンポーネントを小さく分離する。既存のDB接続、認証、メール設定・送信クライアント、回数制限、共通UIを再利用し、新しいライブラリは追加しない。機能のAPIはRoute Handlerに集約する。

### 受付

1. 一般問い合わせフォームは専用URL `/contact`。氏名、メールアドレス、種別（予約について／サービスについて／その他）、件名、本文を入力する。ログイン済みなら本人プロフィールを初期表示し、編集可能にする。
2. 予約問い合わせはお客様の予約確認・詳細にある「この予約について問い合わせる」から開く。予約番号は表示のみとし、種別はサーバー側で「予約について」に固定する。
3. 予約問い合わせAPIはパスの予約番号から本人が閲覧可能な予約を検索し、正しい内部予約UUIDへ関連付ける。一般問い合わせAPIからreservation_idやuser_idを自由指定できないようにする。
4. 問い合わせ本体と受付確認メールの送信待ち記録を同じDBトランザクションで保存し、INQ-1001のような番号をDB採番・一意制約で発行する。
5. 保存後、既存設定の送信元から受付確認メールを送る。問い合わせ番号・件名・本文・日本時間の受付日時、予約問い合わせのみ予約番号を含める。
6. 受付メールに失敗しても問い合わせは削除しない。保存済みの番号とメール未送信を画面に表示し、再試行でも問い合わせを二重作成しない。管理者詳細から受付メールの状態確認・安全な再送を可能にする。

非会員予約については、現状では安全な予約照会の手段がないため、予約紐づけ機能を有効にしない。未ログイン利用者には一般問い合わせを案内する。一般問い合わせに書かれた番号を根拠として予約情報を自動表示したり、予約へ自動関連付けしたりしない。

### 履歴・閲覧

- `/contact/history`と詳細で、認証済みUID本人の問い合わせ・送信成功した管理者回答だけを表示する。
- 匿名で送った問い合わせは、後日のログイン時にもメールアドレス一致だけで取り込まない。匿名利用者の履歴照会画面は作らない。
- 管理者一覧は20件/ページを初期案とし、上限100件。受付日時＋内部IDの降順で安定した並びにする。
- 対応状況・種別・キーワード（問い合わせ番号、件名、氏名、メールアドレス）をサーバー検索する。件数とページ情報も返す。
- 管理者詳細には問い合わせ・回答履歴・関連予約・メール状態を表示し、既存の予約詳細を開く導線を設ける。

### 回答と状態管理

- 問い合わせ時に保存した宛先をサーバーで取り出す。フォームも変更不可。APIに任意の宛先・From・CC/BCCを指定できる設計にはしない。
- 件名の初期値は `Re: 元の件名`、本文は入力。問い合わせ番号・予約番号をサーバー側で付ける。
- 未対応→対応中・完了の手動変更、送信成功→回答済みを実装する。「回答済み」はメール送信成功処理だけが設定する。
- 完了後に追加回答が必要なら対応中へ戻してから回答する。問い合わせと回答は1対多なので、回答を上書きしない。
- 利用者には送信成功分だけ表示し、管理者には送信待ち・失敗・結果不明も表示する。

## 3. DB変更案

既存の単数形命名に合わせ、基本の追加テーブルは2つ。

| テーブル | 主な項目 |
| --- | --- |
| `inquiry` | UUID、公開問い合わせ番号（一意）、認証済み本人のFirebase UID（匿名はNULL）、予約UUID FK（一般はNULL）、氏名・メールの申請時スナップショット、種別、件名、本文、対応状況、受付日時、更新日時、競合確認用revision、受付の重複防止キー・入力内容ハッシュ |
| `inquiry_reply` | UUID、問い合わせUUID FK、回答した管理者のFirebase UID・表示用情報、件名、本文、送信状態、Resend message ID、送信日時、作成日時、回答の重複防止キー・入力内容ハッシュ、初回試行日時・最終試行日時・試行数・送信リース期限・安全なエラーコード |

- 回答状態は問い合わせの4状態と分離し、pending/sending/sent/failed/unknownを管理する。
- 管理者は顧客accountを持つとは限らないので、回答者IDを顧客accountへの必須FKにはしない。認証済み管理者UIDをサーバーから保存する。
- 既存 `email_delivery` を受付・回答メールの送信待ち記録として再利用する。予約IDはNULL。問い合わせ／回答UUIDから安定したdeliveryKeyを作り、本文・宛先を送信前に固定する。
- 管理者一覧の日時・状態・種別、本人履歴のUID＋日時、回答の問い合わせUUID＋日時に必要なインデックスを追加する。
- 予約・顧客の既存データや料金計算・請求には変更を加えない。既存テーブルからの問い合わせ履歴バックフィルもしない。

## 5. 二重送信・DB保存失敗への対処

メールAPIとDBを一つのトランザクションにはできないため、以下を組み合わせる。

1. 送信前に回答・宛先・本文・管理者・重複防止キーとoutboxをDBへ保存する。
2. 同一キーで入力内容が異なる要求は409。二重クリック・再試行は同じ回答ID・キーを使う。ページ再読込後も送信待ち行を再利用する。
3. 問い合わせrevisionと短期リースで同時送信を制御し、他の管理者の古い画面からの送信・状態上書きは409にする。ネットワーク待ちの間、DBトランザクションを開いたままにしない。
4. Resendには回答UUIDから作る同じIdempotency-Keyと固定したメールを送信する。
5. Resend受付成功後、回答のsent・message ID・日時、問い合わせの回答済み、outboxのsentを同じDBトランザクションで確定する。
6. 失敗は未送信確定と結果不明を区別する。送信成功後にDB保存だけが失敗しても、保存してある同じキー・メール内容で再確認して復旧する。
7. Resendの重複防止キーの保持は24時間なので、初回試行から安全な期限内に再試行を限定する。期限を越えた結果不明分を新しいキーで自動再送しない。管理者がResend側で確認する案内を出す。

Resend受付成功を「回答済み」の基準にする。相手の受信箱への到達保証とは区別する。ローカル運用で外部Webhookの公開が必要にならないよう、MVPの復旧は保存済みキーと再試行、期限超過時の手動確認とする。署名付きWebhookによる自動突合は将来拡張候補。

公式資料：[Resend Idempotency Keys](https://resend.com/docs/dashboard/emails/idempotency-keys)、[Webhook署名検証](https://resend.com/docs/webhooks/verify-webhooks-requests)。

## 6. セキュリティ・影響・テスト

- 認証済み利用者のUID、管理者UID、予約との関連はクライアント任せにしない。不正なトークンを匿名として扱い直さない。
- 予約番号・メールアドレス・会社名の一致だけでは閲覧権限を付けない。他人の問い合わせ番号を指定しても内容を返さない。
- Zodで種別・状態・番号・ページ・文字数を検証。初期案は氏名100字、メール255字、件名200字、本文5,000字、JSON全体32KiB。件名の改行は拒否する。
- 本文はプレーンテキスト。Reactの文字列表示、メールのHTMLエスケープを使い、自由入力をHTMLとして実行しない。問い合わせメールではサーバーによる任意URLのリンク生成も避ける。
- 認証操作は既存Bearer方式。公開フォームには同一オリジン検証、Cookieへ結び付けた短期署名トークン、使い捨て識別子、ハニーポット・入力時間チェックを組み合わせる。
- 匿名の初期レート案：同一宛先1分1回・1時間3回、信頼できるIPがある場合は1時間5回、匿名受付全体は1時間50回。管理者回答は既存の認証済み操作制限と宛先別のメール制限を再利用する。数値は実装承認後の初期設定として調整可能にする。
- IPヘッダーを信頼できない構成では共通バケットを使う。厳しくすると他の利用者も制限され得るため、運用時に入口構成・流量と併せて調整する。WAFが未定でもMVPは動作するが、分散したボットをこれだけで完全に排除できるとはしない。
- メールの本人確認を挟まないため、入力ミスや他人のアドレスへの受付メール送信を完全には防げない。この制約は残す。メール一致での履歴公開・予約公開を行わず、送信回数と内容量を抑える。
- 本文・メールアドレス・秘密情報をログへ出さず、本文を含むレスポンスはprivate/no-store。Resendキーはサーバーのみ。送信監査は問い合わせ番号・回答ID・結果・認証済み操作者の識別に限定する。
- 既存の予約状態、店舗割当、人数判定、認証方式は変更しない。メール共通部に必要な拡張は任意引数等で後方互換を保ち、既存メールの挙動を維持する。
- 指定された12項目に加え、送信後DB失敗、同時送信、旧revision、再試行期限、宛先改ざん、匿名の不正な予約関連付け、XSS・ヘッダー改行、レートヘッダー偽装、受付メールだけ失敗した場合の二重受付防止を検証する。
- 新規テストは一時DB／専用PostgreSQLとメールのテストクライアントで実施。実在のお客様へテストメールは送らない。PC・スマートフォンの通し確認、`npm test`、`npm run build`を実施する。
