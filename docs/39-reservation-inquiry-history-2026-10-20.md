# 予約ごとの問い合わせ・回答履歴（2026-10-20）

> 追記：回答の公開条件は[メール未送信でも確認できる問い合わせ回答](40-inquiry-replies-without-email-2026-10-20.md)で変更しました。以下の「お客様には送信済みのみ」の記述は変更前の記録です。

状態：実装・ローカルDB反映済み。検証の最終結果は下記に記載。

## 変更内容

- お客様の「予約確認」の各予約に「問い合わせ・回答履歴」ボタンを追加した。
- 管理者の予約詳細と予約承認画面にも同じボタンを追加した。
- ボタンから中央の子画面を開き、その予約に紐づく問い合わせだけを表示する。問い合わせは受付日時の新しい順、10件ずつ表示し、件名を押すと展開する。最初は最新の問い合わせを展開する。
- 展開すると、お客様の問い合わせと管理者の回答を送受信者・日時付きで時系列表示する。複数回答も確認できる。
- お客様には送信済みの回答だけを表示する。管理者は送信待ち・失敗・結果不明の回答も状態付きで確認できる。
- 既存の一般問い合わせ・本人履歴・管理者問い合わせ詳細でも、同じ時系列表示を再利用する。
- 読み込み中、取得失敗、再読み込み、問い合わせなし、ページ操作、閉じる操作を用意した。履歴を閉じると元の予約画面へ戻る。
- 子画面を開くと最新情報を取得し、再読み込みボタンからも更新できる。各問い合わせの本文・回答は展開時に取得する。

## 権限とデータ取得

追加API：

- お客様：`GET /api/reservations/[id]/inquiries/history`
- 管理者：`GET /api/admin/reservations/[id]/inquiries`

お客様APIは失効確認付きの既存Firebase認証を再利用し、予約の所有者アカウントとUIDをDBで照合する。さらに問い合わせのUIDと予約の内部IDの両方で検索する。管理者APIはサーバーで管理者権限を確認する。

本文・回答の取得には既存の本人／管理者用詳細APIを使用するため、番号の書き換えでも他人の問い合わせを読めない。未送信回答はサーバー側でも本人用レスポンスから除外する。一般問い合わせ・別の予約・他ユーザーの問い合わせを、メールや種別の一致だけで関連付けることはない。

予約の内部IDやUIDはクライアントの検索条件として受け付けない。ページと件数のみ検証して使用し、件数は最大20件。重複条件・不正な範囲・未知の条件を拒否する。レスポンスは `private, no-store`。

## 対象外・制約

- 表示するのはシステムに登録した問い合わせと、管理画面から送信した回答。受信メールにお客様が直接返信した内容の自動取り込みや、既存問い合わせへのお客様からの追加返信投稿は今回追加していない。
- 回答作成・再送・対応状況の変更は従来の「問い合わせ管理」で行う。今回の予約画面側は履歴の閲覧用。
- 本人確認できない非会員予約の履歴公開は行わない。
- 外部メールの実到達確認・WAF等の残存課題は [38. 問い合わせ機能](38-inquiry-implementation-2026-10-20.md) と同じ。

完了時の環境：追加インデックスをローカル開発DBへ反映し、検証用サーバーとタブは終了した。ビルド検証のため停止した `localhost:3000` を通常の `npm run dev:local` で再起動した。
