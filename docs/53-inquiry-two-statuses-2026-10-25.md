# 問い合わせの状態を「未回答」「回答済」に統一（2026-10-25）

## 完了内容

問い合わせの対応状況を2種類に統一し、localhost:3000へ反映した。「対応中にする」「完了にする」の手動操作と、完了を解除してから追加回答する運用を廃止。管理者の一覧・詳細・初期フィルター・タスク件数、お客様の問い合わせ履歴に同じ状態を表示する。

## 自動判定

| 条件 | 状態 |
| --- | --- |
| 回答がまだない | 未回答 |
| ログイン済みのお客様へ回答を保存し、履歴へ公開した | 回答済 |
| 未ログインのお客様への回答メールが送信待ち・送信中・送信失敗・結果不明 | 未回答 |
| 未ログインのお客様への回答メールが送信成功、または管理者が送信結果を明示的に確認・終了した | 回答済 |

- 複数回答がある匿名問い合わせでは、未解決のメール配送が残る限り未回答にする。新しい回答の送信開始時も自動判定する。
- メールの配送状態と回答履歴の公開は分離したまま。登録済みのお客様はメール送信に失敗しても履歴で回答を確認できる。匿名のお客様は未送信のまま要対応件数から消えない。
- メールの凍結済み宛先・本文・識別子、重複防止、安全な再送期限、送信結果確認の処理を維持した。
- 未回答件数は永続化された同じ状態で数えるため、サイドメニュー・ダッシュボードと一覧の初期フィルターが一致する。

## 既存データの移行

- 0020_inquiry_two_statuses.sqlを追加。旧状態の名前だけを置換するのでなく、実際の回答・配送状況から再判定した。旧「完了」でも回答がなければ未回答に戻る。
- 問い合わせのenumを unhandled / answered の2値へ変更した。旧値をDBで再登録できない。
- 手動の状態変更APIは管理者認証の後に405で拒否する。古いブラウザーや直接API呼び出しから状態を変更できない。
- 起動前確認にenumの2値チェックを追加し、未移行のDBでは新しい通常環境を起動しない。
- このプロジェクトの開発サーバーと子ワーカーを停止し、既存DBを .tmp/inquiry-status-before-20261025.dump にバックアップ。pg_restore --listで検証（93,254バイト、個人情報を含むためGit対象外）。初期化やデータ削除は行っていない。
- 移行前は未対応2件・対応中1件・回答済み1件・完了1件。移行後は未回答3件・回答済2件。
- 予約11件、問い合わせ5件、回答履歴2件を保持。全29テーブルの件数と行ハッシュを比較し、問い合わせの状態・更新版番号・更新時刻以外に差分がないことを確認した。停止済み通知6件も維持。
- 以前と同じ開発モード（npm run dev:local）でlocalhost:3000を再起動。通知・カレンダーの各ワーカーは従来の承認済み構成を使用する。
