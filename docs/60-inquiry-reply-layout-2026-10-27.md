# 問い合わせ回答画面の情報整理

実施日: 2026-10-27

## 変更

- 主画面を「問い合わせへの回答」とし、問い合わせ番号・状態を1行にまとめた。
- 問い合わせ本文、空き状況の確認ボタン、宛先、回答件名、回答本文を表示。氏名とメールアドレスは宛先行に1回だけ表示する。問い合わせ日時・管理情報や過去の回答を回答フォームの上へ重ねて表示しない。
- 長い問い合わせ本文は本文内でスクロールして確認できる。
- 空き状況の食事日・開始時間・人数を3列にまとめ、自由記入の質問はその下に表示。質問がない場合は不要な案内を追加しない。
- 「受付情報」の子画面へ、受付日時・種別・関連予約番号／予約詳細への移動・受付メールの状態／再試行を移動。
- 「回答履歴」の子画面へ、過去の回答・回答者・回答日時・回答メールの状態を移動。再試行・送信結果の確認と記録は、対象の回答と同じ位置に表示する。
- 送信未完了の回答がある場合は、新しい回答を送れない理由を主画面に短く示し、回答履歴から復旧できる。受付メールの失敗だけでは新規回答を制限しない。
- 入力中の「下書きを保持しています。画面の再読み込み・ログアウトで消えます。」「『送信する』を押すと回答が保存されます。ログイン済みのお客様は履歴画面でも確認できます。」を削除。
- 下書きの保持・閉じる際の選択・定型文の子画面／挿入位置・送信確認・権限・メール再試行の条件を維持。お客様側の問い合わせ履歴の表示は維持する。
- 「閉じる」「回答を確認」を画面下部に固定し、本文のスクロール位置に関係なく操作可能にした。補助操作の成功・エラーは子画面内だけで表示する。

## 実装

`components/inquiries/inquiry-management.tsx` の主画面を整理し、補助操作を `inquiry-admin-support.tsx` に分離。`inquiry-conversation.tsx` は回答だけを表示する指定と、回答ごとの操作欄に対応。既存利用時の表示は変更しない。API・DBの変更なし。

## 検証

- `npm test`: 最終コードで171件成功、失敗0。
- `npm run build`: 最終コードで成功。既知の `.next` 生成権限の問題を避け、必要な権限で実行。既存のHook依存警告2件あり。
- PC1280px・スマートフォン390pxで主画面・受付情報・回答履歴を確認。ページとダイアログの横はみ出しなし。下部の確認ボタンは両サイズで画面内に表示される。
- 主画面のメールアドレスの表示が1回だけで、受付メールの状態・指定の2つのコメントが表示されないことを確認。回答入力後や下書きの再表示後も同様。
- 受付情報の日時・種別・配送状態／再試行への入口、回答履歴0件の案内を確認。予約状況の子画面が希望日時・人数を引き継ぐことを確認。
- 回答本文未入力のフィールドエラー、定型文挿入、固定ボタンからの送信確認、下書きを残して閉じる／再表示を確認。実送信は行っていない。
- 送信未完了の回答があるときは新規回答を禁止し、理由を主画面に表示。履歴内の対象回答から再試行・結果記録へ進めることを確認。
- 架空の配送結果を「メール送信終了」として記録し、確認チェックなしでは実行できないこと、記録後に履歴へフォーカスが戻り、回答済への更新と新規回答の再開ができることを確認。補助操作のメッセージが主画面に残らないことも確認。
- お客様の問い合わせ詳細で元の問い合わせ・保存済み回答が両方表示されることを確認。

検証はPGliteの一時DB・架空データ・疑似認証を使用。最初の配送結果記録の400は検証サーバーが新規回答用のコントローラーへ転送していたためで、検証ルートだけを実APIと揃えて再確認した。製品のAPIや検証条件は変更していない。入れ子の確認画面を閉じる際のフォーカス復帰も修正・確認した。
