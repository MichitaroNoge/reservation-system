# 未ログインからの予約開始

2026-11-03の依頼に基づく採用仕様。

## 予約の流れ

1. 仮想の店舗Webサイトの「予約フォームへ」、または店舗Webサイトに設置する`/reserve`へのリンクから開始。
2. 未ログインのまま利用者区分、仮予約／本予約、日時・人数・メニューを選択。
3. お客様情報の段階で「ログイン」「新規登録」を選択。メールアドレスとパスワード、またはGoogleで認証。
4. 新規のメール登録はメール確認を必須とする。Google等でプロフィールが未登録なら、予約画面内で登録して続行。
5. 予約用のお客様情報・備考等を確認し、本予約はキャンセル規定に同意して申請。

アカウント登録は必須。認証を省略した予約確定・非会員予約の保存は追加しない。予約APIの認証・認可、受付期限、所有者、同意記録、重複申請防止の処理は変更していない。

## 入力の保持

予約途中のログイン・新規登録は別ページへ遷移しない。認証後のプロフィール読み込みやメール確認後も、日時・人数・メニュー・予約種別・選択した予約区分を保持する。アカウントの連絡先は補完するが、予約区分の選択を既定値で上書きしない。

戻る操作は共有の下部操作欄に置く。途中は「前の入力へ戻る」、未ログインの最初の画面は「店舗Webサイトへ戻る」。ログアウト・アカウント変更時の入力消去は維持する。入力は画面内のメモリーで保持し、ページ再読み込みをまたぐ保存はしない。認証情報・個人情報をURLや永続ストレージへ書き込まない。

従来のログイン・登録専用画面、お問い合わせ、予約確認・変更・キャンセルの認証条件は維持する。

## 検証

- `npm run typecheck`、`npm run lint`: 成功。
- `npm test`: 186件成功。認証後の予約区分・日時・人数・メニューの保持、団体予約とアカウント既定区分が異なる場合、未選択時の既定値を検証する3件を追加。
- `npm run test:db`: 69件成功、PostgreSQL専用11件はPGliteではスキップ。未認証の予約APIが401になる既存検証も成功。
- `npm run build:check`: 成功。内部で`npm run build`を実行し、検証用環境と`.next-check`を使用。初回は出力先への書き込み制限で失敗したため、同じ検証に限定して権限を付けて再実行した。
- PC 1280×900、スマートフォン390×844で確認。店舗リンクと`/reserve`直接表示、ログイン後の予約申請完了、新規登録の必須項目エラー・メール確認後の復帰、Googleログイン後のプロフィール登録と予約再開、前の入力への戻り、ログアウト時の入力消去を確認。

UI確認はFirebase／Google認証とメール確認を模擬し、実際のAPIと隔離したPGliteの架空データを使用した。実アカウントの操作・実宛先への送信・本番環境の操作は行っていない。実Google画面や確認メールの配送は今回のUI検証の対象外。
