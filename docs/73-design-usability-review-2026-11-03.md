# デザイン・ユーザビリティの全体レビュー

2026-11-03。既存の共通仕様と、過去の画面改善依頼を基準に実施。

## 対象と方針

顧客側の入口、予約手順・予約確認、プロフィール・認証、問い合わせ・履歴、管理側のナビゲーション、ダッシュボード、予約一覧・詳細、承認・変更・割当、問い合わせ回答、マスタ管理、および共通の入力・表・ダイアログ・ページ送りをコードで確認した。

ブラウザーでは顧客の予約手順と認証、管理側のダッシュボード・予約一覧／詳細・問い合わせ一覧／回答・マスタ管理の入口を確認した。共通部品で直せる操作上の問題を優先し、全面的な画面の作り直しは行っていない。

## 見つかった問題と修正

| 問題 | 修正 |
| --- | --- |
| モバイル管理メニューの後半が横に隠れる | 開閉式の縦メニューへ変更。PCは常時表示。現在位置、開閉状態、44pxの操作領域を確保 |
| 予約の日付・時間・人数が不足しても、無効なボタンしか表示されない | 共通FormFieldとReact Hook Form／Zodで項目別エラーを表示し、最初の不備へフォーカス。既存APIの整数・1〜999名・受付期限条件を反映 |
| 認証フォームでパスワード表示ボタンまで入力ラベルに含まれ、エラーも入力欄に関連付かない | FormField／Inputのid、aria-invalid、aria-describedbyを共用。ラベルと表示ボタンを分離 |
| 予約区分・種別・メニューの選択状態が読み上げで分からない | aria-pressedを追加。業務上の選択方式は維持 |
| メニュー取得中／失敗／0件が区別できない | 選択欄にそれぞれ表示し、その場で再読み込み。既存入力を保持。予約変更画面にも引き継ぐ |
| 手順や管理画面の切り替えでフォーカスが失われる | 新しい見出しへ移動。管理メニューは選択後に閉じる。Escapeでも閉じられる |
| 予約途中の初回プロフィール登録でタイトルが重複し、未完了でも編集だけを閉じられる | 見出しを1つにし、必須の初回登録では編集終了ボタンを表示しない。保存／エラー／戻る操作は維持 |
| お客様情報不足で申請ボタンが無効でも不足項目が分からない | 不足項目名を表示し、氏名・電話・メールの必須／住所の任意を明示 |
| 予約一覧で横スクロールすると予約の識別子が見えなくなる | 予約ID列を左に固定。表領域へフォーカスして矢印キーでスクロール可能にした |
| 並び順と日付検索の意味が読み取りづらい | aria-sortを追加。「予約日」を実際の検索対象である「利用日」にし、開始・終了を個別に命名 |

フォームの共通部品は、項目ごとにエラー行数が異なってもラベル／入力欄の上端をそろえる。新しいページ専用CSSや依存パッケージは追加していない。

## 検証

- 型チェック・Lint・`npm test`成功。通常テスト190件。日時・整数・境界値・項目別の不備を確認する4件を追加。
- `npm run test:db`: 69件成功。PostgreSQL専用11件は既存のPGlite制約でスキップ。
- `npm run build:check`から既存の`npm run build`を実行し成功。検証用設定と`.next-check`を使用。
- PC1280×900、スマートフォン390×844で顧客・管理の主要な変更を確認。顧客フォームは768pxのタブレット幅も確認。
- 管理メニューの開閉・選択後のフォーカス、ソート、予約ID固定、表のキーボードスクロール、詳細の開閉を確認。
- 予約の空欄／小数エラー、修正して次へ、メニューの選択状態、ログイン欄のエラー関連付け、認証後の予約保持、メニュー取得失敗から入力を保った再読み込み、0件の案内を確認。

実際のアプリ画面とAPIを、模擬Firebase認証と一時PGliteの架空データで確認した。実Google認証、実メール配送、本番データの操作は対象外。すべての業務分岐を実ブラウザーで網羅したものではない。認証・認可、予約の受付条件・同意・所有者、実送信・外部連携の仕様は変更していない。
