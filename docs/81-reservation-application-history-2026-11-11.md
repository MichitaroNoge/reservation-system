# 申請・承認履歴

2026-11-11。承認後に申請内容を再確認する改善案について、ユーザーの「提案してくれた内容で修正してください」に基づく採用仕様。

## 画面と対象

- 予約承認、本予約変更承認、予約変更承認、キャンセル承認に「未対応／処理済み」を配置する。初期表示は未対応とし、既存の抽出条件・承認操作を維持する。
- 処理済みは予約ID・お客様名・結果・期間で絞り込み、20件ずつページ表示する。旧記録の処理結果不明も区別して表示する。
- 予約詳細、受入状況、予約変更比較から「申請・承認履歴」を開く。予約単位では未対応も含む履歴を表示し、申請種別を絞り込める。
- 両方の入口から同じ閲覧専用の詳細を開く。承認・変更・再送ボタンは設けない。予約の修正は現在の予約詳細、メール対応は予約通知メールの画面から行う。
- 履歴詳細は申請者・申請／同意日時・処理者・処理日時・理由・申請前／希望内容・処理直前／処理後の内容・同意記録を表示する。比較できる項目の差分を強調する。初回申請には変更前の予約がないため、申請内容のみを表示する。
- 承認結果の通知メールは申請結果とは別の状態として表示し、送信状況を再読み込みできる。送信状態の更新では申請スナップショットを書き換えない。
- 読込中、取得失敗・再試行、0件、非対応の接続先を表示する。狭い画面では表内スクロール、右端の操作固定、内部スクロールと下部の閉じる操作を使用する。

## 保存と業務ルール

`reservation_application_history`を追加する。予約申請（仮／本）、本予約への変更申請、予約変更申請、キャンセル申請に加え、管理者の予約詳細編集・手動ステータス変更を記録する。

| 保存項目 | 内容 |
| --- | --- |
| 申請情報 | 予約、種別、申請識別子、申請日時、申請者UID・表示名・役割、理由 |
| 申請前・希望内容 | 受付時点の予約、希望日時・人数・メニュー、当時の連絡先・金額・団体情報・支払条件・同意記録 |
| 処理結果 | 承認／却下／手動処理、処理日時、処理者UID・表示名・役割 |
| 処理直前・処理後 | 実際に更新した前後の予約情報。申請受付後の変更と区別する |
| 通知の参照 | この処理で作成された通知のキーと作成日時。現在の配送状態は関連する送信記録から取得 |
| 旧記録の区分 | 不足項目を現在の予約で埋めないためのlegacy区分 |

- 申請時の内容は保存済み予約から明示的に選んだ項目を複製する。所有アカウントIDやメール再試行の内部状態を丸ごと保存しない。後日の予約編集、プロフィール・メニュー名称変更で当時の値を置き換えない。
- 変更申請に終了時刻・変更後金額が含まれない場合、変更前の値を希望内容として流用しない。実際の処理後の値は処理結果へ保存する。
- 申請者・処理者はサーバーで認証したユーザーから取得し、クライアント指定のUIDや日時を使用しない。表示は日本時間。期間は処理日時、未対応・処理日時未記録は申請／同意日時で判定する。
- 既存の予約単位トランザクション内で予約・履歴・承認通知の送信予定を保存する。履歴の保存失敗時は承認や通知の送信予定もロールバックする。外部メール配送は従来の処理を維持する。
- 同じ未対応申請の再送では最初の履歴を維持する。却下後の再申請は別の履歴とする。予約変更申請は既存の申請IDに対応付ける。
- 管理者が申請状態を手動作成した場合も、通常の申請履歴と管理者操作を残す。通常の状態遷移、受入不可判定、キャンセル料、所有権・権限、メールの重複防止・再試行制限は変更しない。
- DBの更新トリガーで受付時の項目の変更と処理済み行の再更新を拒否する。承認結果の履歴と、後から変わる配送状態を分離する。
- 通知は保存されたキーと作成日時の両方が一致する送信記録から表示する。同じ予約で別の承認回に使われた記録を推測でひも付けない。特定できなければ「送信記録を確認できません」とし、未送信と断定しない。
- 記録対象は本変更を含むアプリ/APIを経由した操作。旧コード・直接SQL等の全操作を監査する機能ではない。PostgreSQL/Drizzleと検証用メモリーRepositoryに対応し、書込み停止済みの旧Data Connectでは非対応を表示する。

## 過去データ

- 既存の予約変更申請から、保存済みの希望内容・理由・申請日時・処理結果・処理日時だけを移行する。変更前の予約、処理者、処理後の当時の予約は未記録のままにする。
- 本予約申請・本予約への変更申請のキャンセルポリシー同意記録は、同意時の人数・本文・版・日時・認証UIDを移行する。承認を証明する記録ではないため、結果は「処理結果不明」とする。
- 履歴導入以前の未対応申請を新しく処理した場合は、申請時の内容を推測せず、実際の処理直前・処理後・処理者・処理日時を記録する。
- 旧記録の一覧に現在の予約者名を補助表示する場合は「現在の予約名」と明示する。詳細の過去の予約内容には流用しない。
- 保存されていなかった取消申請の日時・内容・処理者や、初回申請の全内容を現在の状態から作り直さない。未記録・表示不能の範囲を明示する。

## DB反映

追加マイグレーションは`drizzle/0022_reservation_application_history.sql`。新規テーブル・インデックス・書換え保護・既存の確実な記録の取込みのみを行い、既存予約の変更・削除は行わない。テーブルが存在する場合は何もしない単一のトランザクション可能なSQLで、再実行しても新しい記録を旧データとして重複取込みしない。

今回のローカル`reservation_system_dev`には、旧認証系の`0021_account_login_email`も未適用だった。今回の履歴機能の追加だけを`assertLocalDatabase`で接続先確認後に個別トランザクションで適用し、既存のDrizzle移行履歴の件数・最新日時が変わらないことを確認した。0021は適用していない。後日、通常のマイグレーションを適用する場合も0022は再実行可能なので重複しない。本番・クラウドへの適用はしていない。
