# お客様向け画面の共通仕様

確定日: 2026-10-28。利用者の基本仕様案の採用・既存画面への適用依頼に基づく。新規のお客様向け画面は本書と`ui-design-system.md`を参照する。

## 共通レイアウト

- 初回アクセス・ページ再読み込み等でログイン状態が未確定の場合だけ読み込み状態を表示し、未ログイン用の入口を仮表示しない。ログイン状態が確定済みの画面間移動では、その状態を引き継ぎ、認証の確認中表示へ戻さない（2026-10-29更新）。
- 未ログインのログイン・新規登録の入口は「仮想の店舗Webサイト」と呼び、開発確認用の店舗Webサイトの代替とする。本番運用の入口は実際の店舗Webサイトを使用する。管理画面への遷移ボタンはこの仮想画面だけに置き、ログインフォーム・登録フォーム・ログイン後の顧客ポータルには表示しない。

- 共通ヘッダー、画面タイトル、本文、必要な注意事項、下部操作欄の順に構成する。画面タイトルは1回だけ表示する。入力ステップ名・本文の小見出しは画面タイトルと区別する。
- フォーム・設定・詳細は最大720px、予約一覧・問い合わせ履歴は最大960pxで中央配置。左右余白は16px、PCは24px。見出し20px・太字、本文14pxを基本とする。共有の意味別トークンと8px以下の角丸を使用する。
- 不要な説明、重複した情報・タイトル、装飾だけの入れ子を省く。キャンセル料・必須条件・入力エラーは関連箇所に表示する。

## 戻る操作と主要操作

- すべての子画面で`CustomerPageActions`を使用し、画面下端の共通操作欄に戻る操作を置く。戻るは枠線付き、主要操作はprimaryボタン。上部の同じ戻るリンク・ボタンは廃止する。
- 通常は右寄せで戻るを左、主要操作を右。主要操作がない場合も同じ欄に戻るボタンを置く。収まらない幅では戻るが上・主要操作が下の縦並びとし、文字を縮小しない。顧客の主要操作と戻るボタンは高さ44px以上。
- 操作欄の実際の高さと端末下端の余白を確保し、本文・最後の入力欄・エラーを覆わない。短い画面でも位置をそろえ、長い画面では本文をスクロールしても操作できる。ダイアログは操作欄より前面に表示する。
- ボタン名と戻り先を一致させる。単なる「戻る」は使用しない。確認ダイアログ内は「入力に戻る」、完了画面は「お手続きトップへ戻る」とする。

| 画面 | 戻るボタンと戻り先 |
| --- | --- |
| 予約申請の最初 | お手続きトップへ戻る |
| 予約申請の途中 | 前の入力へ戻る（入力は保持） |
| 予約確認・一覧 | お手続きトップへ戻る |
| 本予約への変更・予約変更・キャンセル申請 | 予約一覧へ戻る |
| お問い合わせ・問い合わせ履歴 | お手続きトップへ戻る |
| 予約に関するお問い合わせ | 予約一覧へ戻る |
| 問い合わせ詳細 | 問い合わせ履歴へ戻る |
| メールアドレス変更・お客様情報・パスワード変更・アカウント削除 | お手続きトップへ戻る |
| 各申請・送信の完了 | お手続きトップへ戻る |

- 予約一覧・問い合わせ履歴へ戻った際は、元の表示位置・ページ・検索条件を保持する。存在しない検索機能は追加しない。直接アクセスで保存位置がない場合は先頭を表示する。
- 未ログイン向けお問い合わせはログイン画面へ戻る操作を用い、ログイン済みのトップへ誘導しない。

## ログイン後の画面遷移（2026-10-29採用）

- 2026-11-03追加: 予約の入力開始は未ログインでも可能とする。店舗Webサイトの予約リンクは`/reserve`を使用し、仮想の店舗Webサイトにも設ける。利用者区分・予約種別・日時・人数・メニューを選択後、お客様情報の段階でログイン／新規登録を行う。同じ予約画面内で切り替え、選択内容を保持する。Google登録後のプロフィール入力も予約画面内で完了する。申請はメール確認済み・プロフィール登録済みのアカウントに限定し、未認証の申請や非会員予約は追加しない。
- 予約途中の認証後は、選択した予約区分をアカウントの既定区分で上書きしない。プロフィールの氏名・連絡先を補完し、申請前に確認・編集できるようにする。前の入力へ戻っても予約入力を保持する。ログアウト／別アカウントへの変更時は従来どおり入力を消去する。パスワードや予約入力をURL・ブラウザーの永続ストレージへ保存しない。通常のログイン・新規登録画面は従来の動作を維持する。記録: [72. 未ログインからの予約開始](72-customer-booking-before-login-2026-11-03.md)。

- 同じアプリ内の画面移動はNext.jsのLink／router.pushを使用する。同一ポータル内の切り替えは既存の状態切り替えも使用できる。内部の戻る操作にwindow.location.assign・location.href代入・reloadを使用しない。外部サイトへの移動や、障害からの明示的な再読み込みは別とする。
- 戻る操作はCustomerPageActionsを使用し、内部URLはbackHref、同じ画面内の切り替えはonBackで指定する。認証情報を渡すためのURLパラメーターや独自のログイン済みフラグは追加しない。
- useCustomerSessionでFirebaseの確定済み状態をアプリ内で共有する。画面を閉じても認証監視を継続し、ログアウト・別アカウントへの変更を次の画面に反映する。画面ごとにuser=null・確認中へ初期化したり、独自の認証監視を追加しない。
- 共有する認証状態はブラウザーのメモリー内に限る。独自にUserやIDトークンをlocalStorage／sessionStorageへ保存しない。Firebase標準の永続化とサーバー側の本人確認・認可は維持する。
- 初回アクセス・再読み込み・直接URLを開いた場合は認証復元待ちが発生し得る。確認済みの画面から内部移動した場合とは区別する。実際のAPI取得待ち・取得失敗は必要な箇所に表示し、認証待ちとして扱わない。
- お問い合わせ、問い合わせ履歴、履歴詳細の往復、お手続きトップ／予約一覧への戻りもこの仕様に従う。入力破棄確認、送信中の無効化、送信の重複防止、一覧のページ・スクロール位置保持を維持する。
- 新規画面の確認では、初回の認証待ちに加え、ログイン後の往復で文書の再読み込み・確認中コメント・未ログイン画面のちらつきがないこと、画面移動間のログアウト／アカウント変更を反映することを確認する。

実装・検証記録: [64. 顧客画面のログイン状態を保持する画面遷移](64-customer-session-navigation-2026-10-29.md)。

## アカウント操作の子画面（2026-10-29追加）

- トップの「メールアドレス変更」「お客様情報・パスワード変更」「アカウント削除」は、それぞれ独立した画面へ切り替える。トップや設定画面の中にメール変更・削除フォームを展開しない。
- メールアドレス変更は現在のアドレス・新しいアドレス・確認入力・確認メール送信を扱う。確認リンクから戻った結果も同じ子画面に表示する。
- 追加連絡先メールの確認結果は設定画面に表示する。確認済みリンクの再アクセスは元の確認日時を維持して成功とし、未確認の期限切れ・無効アカウント・削除中は無効扱いにする。初期モードの反映をStrict Mode等で再実行しても結果画面をトップへ戻さない。成功は成功色・role=status、失敗はエラー色・role=alertを使用する（2026-11-03レビュー）。
- お客様情報・パスワード変更はプロフィール・ログイン方法・追加連絡先を扱う。メール変更やアカウント削除の操作欄を重複配置しない。初回のプロフィール登録への誘導は維持する。
- アカウント削除は対象アカウント・取り消せない旨の注意・本人確認を表示し、既存の最終確認とサーバーの削除条件を維持する。
- すべて共通の本文幅と下部操作欄を使用する。入力済みで戻る際は破棄確認を行い、処理中は戻る・送信を無効にする。ログイン状態を保持してトップへ戻る。専用URLの直接表示・再読み込みでも顧客画面として判定し、未ログイン時はログイン案内を表示する。

記録: [65. アカウント操作の子画面分離](65-customer-account-screens-2026-10-29.md)。

## ログイン方法の設定（2026-11-03採用）

- トップの入口と子画面のタイトルは「お客様情報・パスワード変更」とする。本文はお客様情報、パスワード変更、Googleアカウント連携、追加の連絡先メールアドレスの順とする。パスワード変更とGoogleアカウント連携は別の操作欄にし、折りたたまず表示する。パスワード未設定なら見出しは「パスワード設定」とする（2026-11-03追加採用）。
- 現在のパスワード欄を操作間で共用せず、Google連携済みという理由だけで本人確認方法を一律に決めない。
- 設定済みパスワードの変更は毎回、現在のパスワード・新しいパスワード・確認入力を求め、Firebaseでパスワード再認証する。Google認証画面は開かない。忘れた場合は既存の再設定メールの手続きへ進める。
- Googleのみでパスワード未設定なら「パスワードを設定」と表示し、Google本人確認によって初回設定する。変更と初回設定はAPIでも区別し、保存時の実際の設定状態で判定する。
- Google連携追加では、サーバーが直近5分以内のパスワード認証を確認できれば再入力を省略。それ以外は子画面で現在のパスワードを確認した後、連携先Googleアカウントを認証する。開始時・確定時ともサーバーで判定し、途中の期限切れはパスワード確認へ戻す。5分は本システムの採用値であり、一般規格による固定値ではない。
- Google連携解除は子画面で解除対象・注意・現在のパスワード・最終確認を表示し、Google認証を求めない。パスワード未設定での解除はUI・APIとも禁止し、先に設定する案内を表示する。
- パスワード変更・Google解除のAPIは、Google認証だけでは実行できない。現在のパスワードはFirebaseへ送って再認証し、アプリAPIやDBには送信・保存しない。変更後の通知とセッション失効・再ログインを維持する。
- 入力済みでトップへ戻るときは破棄確認する。処理中は関連操作と戻るを無効にし、失敗時はエラーを表示。アカウント変更後に前の操作を継続せず、入力を別ユーザーへ引き継がない。

実装と検証: [66. ログイン方法の設定の改善](66-login-method-settings-2026-11-03.md)、[67. パスワード変更の入口と見出しの改善](67-password-change-discoverability-2026-11-03.md)。メール変更・アカウント削除の本人確認方式は今回の対象外で、既存仕様を維持する。

## 入力と状態

- 空き状況の問い合わせ（2026-11-05追加）: 人数は1〜999名の整数。食事日の最小日は日本時間の本日とし、日付変更・画面復帰でも更新する。送信時にも現在の日本時間で検証し、過去日は欄の下に「食事日は本日以降を指定してください。」と表示する。サーバーの項目別エラーも対応する欄へ表示し、入力を消さず修正できるようにする。ログイン有無を問わず適用し、受付済み送信の再試行は既存の重複防止を維持する。詳細は[74の記録](74-inquiry-availability-limits-2026-11-05.md)を参照。
- 2026-11-03レビュー追加: 利用日・開始時間・人数はラベルに必須を明記し、項目ごとのエラーと入力欄を関連付ける。共通FormField／Inputを使用し、横並びでもエラーがない欄の位置を下げない。受付期限の読み込み完了後は次へ進む操作で不足を確認できるようにし、整数・人数上限・日付・時間の既存API条件に合わせる。
- メニューの読込中・取得失敗・選択肢なしを区別し、再読み込みは予約入力を保持する。選択中のメニューと区分はaria-pressedで伝える。予約手順や内部画面の切り替えでは新しい見出しへフォーカスを移す。初回の認証復元を妨げない。
- 予約途中のプロフィール登録は重複タイトルを避け、未登録のままフォームだけを閉じる操作を置かない。お客様情報の不足で申請できない場合は、不足している項目名を表示する。

記録: [73. デザイン・ユーザビリティの全体レビュー](73-design-usability-review-2026-11-03.md)。

- 戻る際に未保存入力を失わせない。同じ画面状態で保持できる入力は保持し、破棄する場合は「入力を続ける」「破棄して戻る」の確認を行う。申請・問い合わせの応答が未確定の場合は既存の再試行・重複防止を維持する。
- 取得中・0件・取得失敗でも戻る操作を利用できる。送信中は戻る・主要操作を無効にし、二重送信を防止する。送信失敗で入力を消さない。
- 認証・本人確認・予約の業務ルール、キャンセル料の確認、保存とメール配送の区別を維持する。主要な保存・送信処理は既存の処理を使用する。
- 予約確認の操作は共有Buttonを使用し、フォント・太さ・サイズをそろえる。「問い合わせ履歴」と「この予約について問い合わせる」は同じ操作行に並べる。履歴0件では履歴ボタンを無効にする。本人が閲覧可能な履歴だけを予約一覧と一緒に一括集計し、予約ごとの有無確認通信を増やさない。件数確認に失敗した場合も予約一覧は表示し、履歴ボタンは取得不可を示して無効にする。

## お客様の予約確認（2026-11-03追加）

- 担当店舗・店舗の割当状況・確認連絡の実施状況は、お客様の予約一覧・詳細に表示しない。管理側の機能・業務判定は維持する。
- 予約一覧はPCで複数件を比較できる密度にする。通常の予約3件を1280×900pxの画面で下部操作欄に隠れず表示できることを確認する。追加の申請状況・長文がある場合も情報を隠して高さを固定しない（2026-11-03追加修正）。
- 日時・予約状況・予約ID・詳細ボタンは同じ行へまとめる。人数16px、メニュー14pxの太字を基本とし、見やすさは文字の大きさだけに頼らない。人数とメニューは隣接表示し、大きな背景帯や重複する余白を設けない。長いメニュー名は折り返して全文を表示。未確定なら「メニュー未確定」とする。ボタンの高さ44px以上を維持する。
- 「一般予約」の区分は一覧・詳細とも表示しない。団体名は一覧に残し、旅行会社向けの区分は詳細で確認できる。予約申請時の区分選択・業務判定は維持する。
- 各予約の「予約内容の詳細」から、予約時に保存された入力内容を子画面で確認できる。現在のプロフィールで予約時の氏名・連絡先を置き換えない。
- 一般予約は氏名・電話番号・メールアドレス・住所・支払条件・備考を表示。団体予約は会社・支店名、予約担当者、当日責任者と携帯番号、団体名・ふりがな・種別・その他、T/C・D/Gも表示する。T/C・D/Gは保存値を表示し、人数に加算しない。保存済みの同意記録がある場合は同じ詳細から確認できる。
- 任意項目が空なら「未入力」、人数の内訳が0なら「0名」と表示し、長文・改行を保持する。画面の追加表示のために予約ごとのAPI取得を増やさず、取得済みの予約情報を使用する。
- 子画面は最大720px。長い内容は本文内をスクロールし、タイトルと閉じる操作を常に利用できる。Escapeで閉じ、元の予約の詳細ボタンへフォーカスを戻す。予約の各申請・問い合わせ・履歴・トップへの戻る操作を維持する。

記録: [68. お客様の予約確認画面の改善](68-customer-reservation-review-2026-11-03.md)、[69. 予約確認の表示密度の改善](69-customer-reservation-density-2026-11-03.md)。

## 実装と確認

- `components/ui/customer-page-layout.tsx`の共通部品を使用する。画面ごとにフッターや戻るボタンのCSSを複製しない。既存フォームの互換調整は共通クラスの範囲に限定する。
- PC1280px・タブレット768px・スマートフォン390pxと、ボタンが収まらない幅で確認する。横はみ出し、キーボード操作、フォーカス、本文との重なり、画面の戻り先、入力保持／破棄確認、取得・送信の失敗状態を確認する。
- `npm test`と`npm run build`を実行し、結果と適用範囲を記録する。実宛先へのメールや実予約の変更は検証に使用しない。
