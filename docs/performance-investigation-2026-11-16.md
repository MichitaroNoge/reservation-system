## 計測方法と安全性

- API：実際のRoute Handler・Repositoryを使用。架空予約1,000件／10,000件、関連メニュー・店舗割当・変更申請・送信済み通知を生成。2回ウォームアップ後7回測定し、中央値・p95・最小／最大・SQL数・JSONバイト数を記録。7回のp95は最大値であり、運用の長期p95ではない。
- ブラウザー：Playwright Coreと既存Chromeを使い、1280×900／390×844で確認。初期表示は毎回新しいブラウザーコンテキストで5回計測。表示対象のDOMを待ち、描画完了・選択値も確認。操作では準備時間を除外し、対象操作から応答・DOM更新・2フレームまで測定する。`readyMs`にはPlaywrightの待機・制御時間も含まれ、FCPと同義ではない。詳細ダイアログの操作時間は枠が表示されるまでで、空き状況の読み込み完了時間とは別に扱う。
- ブラウザーは実際の検証ビルドを使用。APIだけを同じプロセスの隔離DB用ハンドラーへ接続する。**APIハンドラー単体の時間は、Next.js内部のHTTPルーティングや実Firebaseの通信時間を含まない**。ブラウザー計測はループバックのプロキシ・HTTP・JavaScript・描画を含む。
- Firebase SDKの外部通信は架空の応答に置換し、サーバー側SDKのトークン検証もテストfixtureを使用する。実アカウントは操作しない。失効確認の指定、所有権、権限、回数制限、排他、同意、履歴、送信重複防止はアプリ側で維持する。実認証のネットワーク遅延は未計測。
- 実DB・メール・OAuthの設定を引き継がない既存の `validationEnvironment()` を使用。`.env.local`／`.env.development`は書き換えない。メール・カレンダーワーカーは起動しない。問い合わせ・Google用の秘密値を設定していないため、匿名challengeとGoogle認証の一部は503。問い合わせのブラウザー計測はその条件での初期表示で、正常な匿名送信の速度を意味しない。
- PostgreSQLの補助計測は、既存ポート5433とは別の**使い捨てコンテナ** `reservation-performance-cf39`（127.0.0.1:55439、512MiB、一時領域）を使用。固定のテスト用DBだけを初期化する。PGliteとの数値を横断比較せず、別表に記載する。
- JSサイズはブラウザーが受け取ったscript応答本文の展開後バイト数。gzip転送量・ビルド表示のFirst Load JSとは別の指標。HTTPキャッシュを使わない条件で比較する。

生データと画面記録は `.tmp/performance/` に保存。主要なサンプル・SQL計画の永続記録は [performance-results-2026-11-16.json](performance-results-2026-11-16.json) に保存。外部通信の実測値や推測値は補完しない。

## 発見した問題と反復改善

### 1. 1件の操作で全予約を読み込む

予約更新、承認、通知送信、受付済み申請の再試行などで `listReservations().find(...)` が使われていた。予約・メニュー・割当・同意を含む全明細を取得してから1件を探すため、クエリ数が1でも読み込み・JSON変換・転送・メモリ確保が増大する。

既存の `getReservation()` による予約ID取得を共通の `findReservation()` で利用した。既存トランザクションのRepositoryをそのまま渡し、競合チェック・履歴・ロールバックを維持する。旧Repositoryには従来の読み取りにフォールバックする。

1万件の更新APIは **849.98ms → 第1回31.08ms → 第3回29.00ms**。1件の照合に全件取得を使わない回帰テスト、更新競合409、履歴・通知の原子性を確認した。

### 2. 待機中も通知履歴・予約をすべて取得する

承認通知は対象0件でも送信済み履歴を読み込み、確認通知は全予約を読み込んでいた。DBで未送信・停止・再試行回数・次回時刻・予約日・状態を絞り、元のサービス側の判定も維持した。`checked`の総件数は維持する。通知1件の取得も配送キーによる取得に置き換えた。

1万件・対象0件で、承認ワーカーは **568.13ms → 第1回6.30ms → 第3回5.44ms**、確認ワーカーは **862.08ms → 9.61ms → 8.46ms**。

再調査で通知管理も全予約を読んでいることを確認。まず送信済みなら予約取得を省略して **1,009.37ms → 187.58ms**、続いて未送信の存在確認だけで終了できる経路を追加して **2.24ms**になった。未解決通知がある場合の照合は従来のまま維持し、予約の検索をMapに変更。復旧キーのハッシュは比較ループ外で計算する。

### 3. 空き状況の確認が全履歴を取得する

承認の詳細を開くと、予約1件の詳細に加えて空き状況APIが全予約を取得していた。対象予約をIDで取得し、利用日と現在のメニューの最大所要時間から**取りこぼしを避けた日付範囲**を求め、候補だけをDBで取得する。最終的な重なり・人数・状態・受入不可の判定は既存関数を使用する。前日からの日またぎ、3日メニュー、開始時刻不明、来店済み・キャンセル申請中等について全件走査との一致を検証した。

### 4. 初期表示のJavaScriptと読み込み順

入口はブラウザーで描画してからeffectで画面を判定し、選んだ画面のJSを追加取得していた。判定をServer Componentに移し、選択されたClient ComponentをNext.jsがプリロードできる構成にした。管理／お客様画面の設定、履歴詳細等は表示時に読み込む。カレンダーと承認ダイアログの分割は操作時間が悪化したため戻した。ログインセッションと入力保持の仕組みは変更しない。

第2回の5回中央値は、予約入口 **554.89ms → 353.15ms**、管理ログイン **523.24ms → 313.91ms**。JSは予約入口873,022→850,909bytes、管理ログイン1,061,126→897,976bytes。顧客ログイン・問い合わせの表示時間の差は小さく、明確な改善とは判断しない。初回サーバー起動直後の1サンプルやFCPには悪化もあり、中央値だけで隠さず最終表に記録する。

### 5. 一覧遷移に不要な200ms待機

テキスト検索用のdebounceが、一覧を開く・ページ送り・更新でも入っていた。文字入力の変化だけ200ms待ち、画面を開く・ページ・再試行・更新は直ちに読み込む。古い応答の中断、フィルター変更時の先頭ページ復帰、回数制限は維持する。

新規予約のフォームを開く際には、フォームが使用しない `/api/customers` も呼んでいたことをブラウザーで確認。顧客一覧はアカウント管理画面でのみ取得する。

開発モードのStrictModeでは、詳細ダイアログの最初のeffectが破棄された後もトークン取得完了時に空き状況APIを呼んでいた。トークン取得後に既存の中断フラグを確認するように修正。5回すべてで1回の操作あたり2リクエスト→1リクエストとなった。StrictMode・認証・失効確認は維持する。

### 採用しなかった試行

一覧の予約ID照合クエリを削るためソート用キーに予約コードを含めたが、1万件の日本語メニューソートは約130ms→140msで、明確な性能改善を確認できなかった。コードと全件キーの転送量を増やす変更は戻した。ソート・件数・検索の既存仕様は維持する。

カレンダーを遅延読み込みすると、初回のカレンダー遷移が117.51ms→433msに悪化した。承認ダイアログとともに通常のimportに戻し、最終計測は133.53ms（各1サンプル）。低頻度の設定類の分割は維持する。FCPと最初の表示サンプルには最終版でも悪化があり、全表示指標が改善したとは判断しない。

### 併せて確認・修正した不具合

前回の顧客向け15分刻みの共有schemaを管理者フォームが継承し、管理者も分単位で登録できなくなる箇所を発見。管理者の開始時刻を従来のHH:mm検証に戻し、19:07の登録・既存予約編集をテストで保証した。顧客は00・15・30・45分のみを維持する。

## 未計測・残課題と追加改善候補

- 実Firebaseの署名・失効確認、Google OAuth、Resend配送、Cloud SQL／Data Connectの実ネットワーク遅延は未計測。速度のための認証結果のリクエスト間キャッシュや安全性の省略は導入していない。
- Server Actionsは非使用のため該当処理なし。外部画像や画像配信が主要な読み込みを占める構成ではない。Googleログインの外部スクリプトは今回ブロックしており、実配信時間は未計測。
- PGliteはPostgreSQL互換の隔離テストであり、本番の同時接続負荷・ネットワーク・I/Oの代わりにはならない。実PostgreSQLの補助計測も、ローカル・ウォーム・1万件・単一クライアントの範囲。
- 予約一覧は既に50件にページ分割されている。日本語自然順を維持するソートは対象全件のID・キーを取得する。大量データでは仕様互換の照合順設計や検索用インデックスを、実クエリ計画を見て別途検討する。
- 顧客本人の予約一覧、対象別の承認一覧、通知管理の未解決ありの経路は、対象件数自体が大量の場合にページ分割・追加の絞り込みを検討する。保存・同意・履歴の詳細を単に削除して高速化しない。
- 今回のDB改善は既存の予約コード一意インデックス・利用日インデックスを使用する。未送信履歴の全走査は実PostgreSQL1万件で約0.8msだったため、新しいインデックスやマイグレーションは追加しない。
- PCの観測時はメモリの余裕があり、Dockerも待機状態だった。開発コンパイルとアプリの全件取得は区別すべきで、現時点の観測だけでPC買い替えが必要とは判断できない。
