### 性能の再計測条件

`npm run perf -- db quality-before|quality-after 10000 --only=change-submit-api`。同じ架空予約1万件・変更履歴1万件、PGlite、Node 24.18.0、ウォームアップ2回＋計測7回。外部認証はfixture、実送信なし。中央値1,822.31→65.58ms、P95 1,861.28→70.72ms。クエリ数19と返却サイズ501Bは同じ。クエリ回数だけでは見えない関連行の取得・変換量が原因である。実Cloud SQL/Firebaseのネットワーク時間や本番の推定値ではない。JSONは`.tmp/performance/quality-before-db-10000.json`と`quality-after-db-10000.json`。

同じ最適化後の処理を使い捨てPostgreSQL17.11でも実測し、中央値69.84ms/P95 87.67ms、23クエリ/501Bだった（`quality-postgres-db-10000.json`）。ドライバーが異なるため、PGliteの改善前値との性能比較には使わない。本番ビルドの管理登録操作は架空1000件で145msの単発観測、迅速入力後の検索APIは1回。これは包括的なLCP/INPや本番負荷の測定ではない。
