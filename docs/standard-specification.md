# 機能追加時に参照する標準仕様

作成日: 2026-10-25
状態: 2026-10-25の全体デザイン統一依頼に基づき、UIの統一方針を採用。業務ルールは既存の確定仕様を維持。未確定の性能目標などは引き続き提案として区別する。

## 1. 目的と読み方

機能追加のたびに画面の見た目や操作が変わらないよう、実装前に参照する入口とする。利用者の最新の依頼を優先する。本書の提案部分は未承認のため、自動的な実装要件にしない。各機能の詳細、実装日、テスト結果は既存の仕様書・作業記録へリンクし、同じ情報を過剰に複製しない。

仕様と現状の実装が食い違う場合は、現状を標準と決めつけず差分として報告する。認証情報、APIキー、実在のお客様の個人情報は記載しない。

### 2.3 入力・メッセージ・画面状態

- 必須／任意と入力項目名を分かるようにし、入力エラーは対象項目の近くに表示。
- 読込中、失敗、0件、成功、保存中・送信中の操作不可を用意。送信の二重実行を防ぐ。
- エラー時は原因の概要と次の操作を示し、内部エラーや不要な技術情報をお客様へ表示しない。
- 問い合わせの回答下書きは同一ログイン中に保持し、閉じるときは保持・破棄・入力継続を選べる。現在は画面再読み込み・ログアウトで消える。
- 回答入力中の下書き保持・保存／履歴公開についての常時コメントは表示しない。下書きを閉じる確認と実際の送信確認は維持する（2026-10-27、60-inquiry-reply-layout-2026-10-27.md）。
- 問い合わせ回答テンプレートは定型文の挿入に使用し、全文を置き換えない。「定型文を挿入」で本文のカーソル位置へ追加し、既存本文・選択範囲の文字を保持する。本文の位置を指定していなければ末尾に追加する。複数の定型文を組み合わせて編集でき、件名・宛先は変更しない。合計10,000文字を超える挿入は本文を保持して拒否する（2026-10-27、59-inquiry-reply-snippet-insertion-2026-10-27.md）。
- 「定型文を挿入」は回答本文の枠の左下に配置し、選択は子画面で行う。子画面は定型文の名前・本文プレビュー・挿入ボタンを表示。長文は160文字・最大3行まで表示し、マウスを重ねると全文を確認できる。「全文を表示」でも展開でき、スマートフォン・キーボードでも確認可能。子画面を閉じた後の挿入位置とフォーカスを維持する（2026-10-27追加依頼、59-inquiry-reply-snippet-insertion-2026-10-27.md）。
- 定型文の挿入成功コメントは表示しない。挿入後は本文に戻り、そのまま編集を続けられる（2026-10-27追加依頼）。
- 定型文選択の子画面はタイトルと操作を表示し、挿入方式・長文確認方法についての常時説明文は表示しない（2026-10-27追加依頼）。
- 定型文選択は有効な文例の一覧と全文を1回のAPI・DB取得で読み込み、同じ回答画面内では取得結果を再利用する。ページ送り・子画面の開き直しでは再取得しない。再読み込み操作は保持結果を無効にして再取得し、取得失敗は保持しない。挿入直前の最新本文・有効状態の確認は維持する。回答画面を閉じる・再読み込み・ログアウトで保持結果を破棄し、ブラウザーの永続ストレージには保存しない（2026-10-27追加依頼、59-inquiry-reply-snippet-insertion-2026-10-27.md）。
- 重要な破棄・削除には確認を設ける。通信失敗時に入力内容を意図せず失わないようにする。
- 顧客のキャンセル申請は予約情報の見出しを「ご予約内容」とし、共通の下部操作欄で「予約一覧へ戻る」を「キャンセルを申請する」の左隣に配置する。申請画面上部の重複した戻る操作と、対象予約の確認・ログイン中のアカウントに紐づく予約だけ申請できる旨の常時説明文は表示しない。キャンセル料の案内・申請前の確認・本人確認は維持する（2026-10-28共通化、62-customer-screen-alignment-2026-10-28.md）。

参照: 52-ux-high-priority-fixes-2026-10-24.md。

### 2.4 用語と問い合わせの扱い

- お客様に示す予約種別は「仮予約」「本予約」。不要な状態の追加・改称をしない。
- 問い合わせ状態は「未回答」「回答済」の2つ。初期フィルターは未回答。「対応中」「完了」の手動運用は廃止済み。
- 会員への回答は保存・履歴公開で回答済。匿名への回答は配送状況も加味する。詳細な判定は53の記録を参照し、画面だけで別の判定をしない。
- 予約に紐づかない問い合わせの新規選択肢は「空き状況について」「その他」。過去データの表示と新規選択肢を混同しない。
- 空き状況の問い合わせは食事日・開始時間・人数が必須、その他質問は任意。人数は1〜999名の整数。新規受付の食事日は送信時点の日本時間で本日以降とし、ログイン有無を問わず画面とサーバーで確認する。同日の過去時刻は指定できる。日付変更後も再検証し、エラーでは入力を保持する。受付済みの同一送信の再試行や過去の履歴閲覧・回答は維持する。詳細は74の記録を参照。管理者がカレンダーを見て受入を判断する。
- 回答の保存・履歴公開とメール配送の成否を分離。メール失敗で回答履歴を消さない。

参照: 46-general-inquiry-categories-2026-10-22.md、47-availability-inquiry-fields-2026-10-22.md、50-inquiry-availability-calendar-2026-10-22.md、53-inquiry-two-statuses-2026-10-25.md。

### 2.5 予約の業務ルール

- 受入上限は店舗別ではなく全体で設定。共有スペースを含む。T/Cは入力された予約人数に含まれ、追加加算しない。
- 受入不可の日時、予約・変更申請締切の日数はマスタ管理「その他」で設定。締切日数の初期値は3日。
- 対象外の人数だけの変更を前日まで受け付ける例外を含め、詳細条件は既存ロジックと仕様書を参照する。キャンセル申請を予約締切や料金発生だけを理由に拒否しない。
- 本予約の取消・基準人数から50%以上の減員は、キャンセル料の事前案内対象。本予約申請・本予約への変更時は同意を記録。金額の自動請求機能は不要。
- 同一予約への同じ店舗の重複割当を認めない。
- 管理者Googleカレンダーの連携対象は承認後の有効な予約。キャンセル済・却下を含めない。

参照: 17-global-settings-2026-10-16.md、18-acceptance-blocks-2026-10-16.md、21-reservation-lead-days-2026-10-16.md、28-unique-store-assignments-2026-10-16.md、35-cancellation-fee-notice-2026-10-19.md、36-confirmed-policy-consent-2026-10-19.md、41-google-calendar-integration-2026-10-20.md。古い記録の反映保留状況はその時点の履歴であり、現在の適用状況と区別する。

### 2.6 認証・データ・外部連携

- 2026-11-03レビュー補足: 受付メールの結果不明な再送は、キュー経由・定期処理からの直接呼出しとも、保存済み配送日時から23時間を超えたら停止する。送信済み記録から復旧する際は本来の送信日時を保持し、再送しない。バッチに指定した送信タイムアウトは個別処理へ引き継ぐ（71-system-review-2026-11-03.md）。
- 追加連絡先の確認は有効な所有アカウントについて行い、削除中は確認しない。未確認リンクのみ有効期限を判定し、確認済みリンクの再アクセスでは最初の確認日時を保持して成功扱いにする。トークン付きURLはNext.jsの開発アクセスログへ出さず、確認応答はno-store／no-referrerとし、結果は設定画面に表示する。
- 2026-11-03採用: ログイン方法の設定はパスワードとGoogle連携を分離。設定済みパスワード変更とGoogle連携解除は現在のパスワードで再認証し、Googleの再認証を求めない。初回パスワード設定はGoogleで確認する。新しいGoogle連携では直近5分のパスワード認証を再利用し、期限切れのみ再入力する。APIも操作別に認証方法と最新の設定状態を確認する。詳細はcustomer-screen-standard.mdと66-login-method-settings-2026-11-03.mdを参照。

- Firebase Authenticationによる認証を維持し、サーバーで管理者権限／本人のアクセス権限を確認する。画面のボタン非表示だけで認可しない。
- 顧客のログイン後トップは予約申請と予約確認・変更・キャンセルを上部に配置。「メールアドレス変更」の隣の「お客様情報・パスワード変更」から別画面へ移動する。入口・画面タイトルにパスワード変更を明示し、お客様情報、パスワード変更（未設定ならパスワード設定）、Googleアカウント連携、追加の連絡先の順に表示。パスワード欄は折りたたまない。初回のプロフィール未登録時も設定画面で登録し、完了後トップへ戻る（2026-11-03更新、67-password-change-discoverability-2026-11-03.md）。
- 認証情報とお客様プロフィールを分離。メールアドレスの一致だけで別アカウントや過去の予約を自動連携しない。
- 予約時のお客様情報はスナップショット。プロフィール変更で過去予約を変更しない。
- Next.js／React／TypeScript、PostgreSQL／Drizzle、既存Resendの構成を再利用。不要なライブラリ・DB変更を避ける。
- 通常の確認先はlocalhost:3000。クラウドDBへの反映は別依頼。既存データの初期化・削除を通常の開発手順にしない。
- 保存完了とメール送信完了を区別する。再送は既存のキュー・重複防止・試行制限を再利用し、停止済みメールを勝手に再開しない。

参照: ../README.md、04-database-design.md、07-authentication-and-security.md、45-performance-improvements-2026-10-22.md。

### 2.7 検証と報告

- 2026-11-03追加: 自律開発の基本検証は`npm run verify`（型生成・型チェック・警告0件のLint・通常テスト・一時PGlite・検証ビルド）と`npm run test:auth`。実DB・メール・OAuthの認証情報を引き継がず、検証ビルドは`.next-check`へ分離する。CIも同じ手順を使う。実PostgreSQLテストは専用DBを初期化するため基本検証には含めない。手順と範囲はvalidation.mdを参照。
- 機能に適したテストとnpm test・npm run buildを実施。UI変更はPCとモバイルで重要な操作を確認。
- 認証・権限・DB・メールに関わる場合は正常系だけでなく拒否・失敗・再試行・競合も確認。
- 通常の検証は架空データと隔離環境を優先。実宛先への送信や既存データの変更と区別する。
- 完了報告は変更内容、確認結果、未確認事項、実行環境への反映状況を明記する。実装済と稼働環境反映済を区別。
- 作業記録をdocsへ残す。秘密情報や実在のお客様の情報を検証画像に残さない。

## 4. 今後の保守方法

- 標準仕様の各項目には「確定」「提案」「廃止」の区別、更新日、根拠の依頼／仕様書、対応する共通部品を持たせる。
- 作業開始時は本書と対象機能の詳細仕様を読む。新しい依頼で変更された仕様は、作業記録だけでなく標準仕様・詳細仕様も同時に更新する。
- 新規画面は共通ひな形から作る。既存画面は変更時に段階的に揃え、無関係な画面を一括変更しない。
- まず一覧の検索条件・件数・枠・ページ送りを統一し、次に詳細画面、その後マスタ画面へ広げる。
- UIの具体値と部品はui-design-system.mdへ集約し、本書は参照先と共通の業務ルールを整理する入口とする。今回の統一で検索仕様・締切・認証・データモデルは変更していない。
