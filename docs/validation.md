# 開発時の検証環境

更新日: 2026-11-15。変更範囲に応じて検証を選ぶ運用を採用。既存のNext.js 15・TypeScript・ESLint 9・Node.js test runner・tsx・PGlite・Firebase CLIを維持し、共通UIの確認にStorybook 10.6.7／Viteを追加した。

## 最初の準備と標準手順

Node.js 22.12以上とnpmを用意する（Storybook／Viteの対応条件を含む）。適した既存のworktreeと導入済み依存を優先して使い、`npm ci`は初回、lockfile変更、依存の不整合など必要な場合だけ実行する。通常の検証にはDocker・実DB・実Firebaseアカウント・Resendの認証情報は不要。

日常の修正では次の区分で必要なチェックを選ぶ。この方針は、以前の「すべての修正で`verify`と`test:auth`を実行する」手順を更新する。複数区分に該当する場合は必要なチェックを組み合わせる。

| 変更区分 | 必要な確認・コマンド | 原則として対象外 |
| --- | --- | --- |
| 文書のみ | `git diff --check`、変更内容・参照リンク・指示の整合性 | 型チェック・Lint・テスト・ビルド |
| 文言・見た目のみ | `npm run typecheck`、`npm run lint`、影響する箇所のPC／モバイル表示 | 通常テスト・DBテスト・認証テスト・ビルド |
| UIの操作・状態・入力検証 | 型チェック・Lint・関連テスト・`npm run build:check`、変更した操作と失敗時の画面確認 | DB・認証に影響しない場合のDB／認証テスト |
| API・業務ロジック | 型チェック・Lint・`npm test`・`npm run build:check`、変更した正常系・拒否／失敗系 | DB・認証に影響しない場合のDB／認証テスト |
| DB・永続化・マイグレーション | APIの区分に加え`npm run test:db`。制約・ロールバック・再試行・競合など影響する条件 | 認証に影響しない場合の認証テスト。実PostgreSQLは別途必要性を判断 |
| 認証・認可・セッション | APIの区分に加え`npm run test:auth`。DBの所有権・権限制御に影響する場合は`npm run test:db`も追加 | 影響のないDB機能の追加検証 |
| 広範囲の変更・影響範囲が不明・アプリ公開前 | `npm run verify`と`npm run test:auth`による全体検証 | 専用DBの初期化を伴う実PostgreSQLテストは自動追加しない |

表示条件、送信処理、入力の妥当性、権限、APIとの契約を変える修正は「文言・見た目のみ」に含めない。依存・ビルド設定の変更は検証ビルドを含め、共有基盤に広く影響する場合は全体検証とする。文書中のコマンド・設定例・運用ルールの変更は、例の実装や参照先との整合性も確認する。今回の検証方針の文書変更自体は「文書のみ」として扱う。

関連テストは既存の安全な手順で対象を絞れる場合に限って絞り込む。`npm test -- tests/reservation-history.test.ts`、`npm run test:db -- tests/db/reservation-history.test.ts`のように、既存の検証コマンドへ現在存在するテストのパスを指定できる。複数指定も可能。通常テストは`tests/*.test.ts`、DBは`tests/db/*.test.ts`だけを許可し、任意スクリプト・追加フラグ・fixtureは拒否する。指定しても同じ隔離設定を維持し、指定なしは従来どおり全件実行する。該当する関連テストがなければ`npm test`を使用する。DB・認証の検証が必要な場合も、下記の既存コマンドと隔離設定を使い、独自の直接実行で実認証情報を引き継がない。

全体検証を行う場合:

```powershell
npm run verify
npm run test:auth
```

`verify`は以下の表の型・Lint・通常テスト・DBテスト・検証ビルドを順番に実行し、失敗した時点で非0終了する。認証エミュレーターは別コマンドにし、ポートの用意が必要な検証と区別する。CIでは従来どおり両方を実行する。

## 準備・再検証・報告

- 調査は標準仕様の該当項目と変更に関係する仕様・実装へ絞る。無関係な文書の通読や全体調査を毎回行わない。
- 既存の安全な検証環境・架空データを再利用し、軽微な変更のたびに専用サーバーや検証画面を新設しない。再利用できない場合も、変更の確認に必要な範囲だけ用意する。
- 同じ最終コードと関連設定で成功したチェックは繰り返さない。追加修正では影響するチェックだけ再実行し、失敗や不確実な影響があれば範囲を広げる。依存・環境・設定が変わって結果が無効になった場合は再確認する。
- 各コマンドを個別に実行して必要な全体検証を満たした場合、同じ内容の`verify`をもう一度実行する必要はない。
- 作業記録と完了報告には、変更の区分、実行した検証と結果、対象外とした検証の理由を簡潔に残す。文書だけの変更は関連文書の更新と完了報告でよく、専用の作業記録ファイルの新設は不要。
- 実行不要と判断した検証と、必要だが環境の制約で実行できなかった検証を区別する。失敗を隠したり、テストを無効化して完了扱いにしない。

## コマンド一覧

| コマンド | 検証対象・実行条件 |
| --- | --- |
| `npm run typecheck` | `next typegen`でルート型を生成してから、`tsc --noEmit --incremental false`。事前のビルドを不要にする |
| `npm run lint` | app・components・lib・scripts・testsと設定ファイル。警告も失敗として扱う |
| `npm test` | テスト用tsconfigでコンパイルし、現在の`tests/*.test.ts`に対応するJSだけをNode test runnerで実行。削除済みテストの古い生成物を実行しない |
| `npm run test:db` | 現在の`tests/db/*.test.ts`を自動列挙し、独立した一時PGliteで直列実行。既存の開発DB・Docker・クラウドは使用しない |
| `npm run build:check` | ダミー設定で既存の`npm run build`を呼び出し、専用の`.next-check`へ本番ビルドの検証結果を出力 |
| `npm run verify` | 上記5段階の統合実行 |
| `npm run test:auth` | demoプロジェクトのAuthエミュレーターを起動し、実Firebase SDKによる契約テストを実行して停止。ホスト127.0.0.1、ポート9099・4400・4500 |
| `npm run test:auth:contract` | 既に起動した専用エミュレーター内で使う内部コマンド。通常は`test:auth`を使う。テスト冒頭でローカル接続先を検査する |
| `npm run build` | 通常のアプリ用ビルド。実行環境の設定を使って`.next`へ出力するため、日常の自律検証は`build:check`を使う |
| `npm run storybook` | ダミー設定で127.0.0.1:6006に共通UIの確認環境を起動。`dev:ui`は同じ処理への互換コマンド |
| `npm run build-storybook` | 同じダミー設定で`storybook-static/`へ静的ビルド。Storyのplay関数はこのビルドだけでは実行しない |
| `npm run test:db:postgres -- --confirm reservation_system_test` | 任意の実PostgreSQL検証。専用ローカルテストDBを初期化するため、通常の`verify`・CIには含めない |

通常テスト・PGliteのDBテスト・検証ビルドの子プロセスでは、実メール・OAuth・サービスアカウント・Cloud SQL設定を除去／無効化し、DB接続先とFirebaseプロジェクトを検証用に固定する。親のシェル環境や環境ファイルは書き換えない。DBドライバーはPGliteに固定し、既存の`DB_TEST_DRIVER=postgres`や初期化の確認値を引き継がない。

`.next-check`の生成物はダミーのFirebase設定を含む検証専用で、配布しない。開発用`.next-dev`、通常ビルド`.next`と区別する。検証コマンドはアプリサーバー・メールワーカー・カレンダーワーカーを起動しない。`dev:local`／`start:local`はワーカーを起動するため、テスト用コマンドの代用にしない。

## 検証範囲

- 共通UIの目視確認は`npm run storybook`（`dev:ui`も同じ動作）と127.0.0.1:6006を使用する。旧`/design-system`は廃止。既存のvalidationEnvironmentで外部認証情報を除き、StoryはAPIを呼ばず架空データを使う。PC1280px・モバイル390px・共有レイアウトでは768pxと境界幅で確認し、実業務フローの確認範囲とは区別する。Storyや設定・依存を変更した場合は`npm run build-storybook`も実行する。Docs・Controls・Viewportを使用し、playの成功はStorybookのInteractionsで確認する。静的ビルドだけではplayの実行成功を保証しない。Playwright／Vitest addonや画像差分の自動検証は未導入。

- 通常テスト: 予約・認可・キャンセル条件・通知・問い合わせ・顧客画面の回帰、検証環境の安全な固定を確認する。
- PGlite: SQLマイグレーション・Repository・API・本人の所有権・ロールバック・メール／カレンダーの送信予定などを検証。テストログの送信成功はモックの結果で、実メールの送信ではない。
- 実PostgreSQL限定のテストはPGliteではskipする。ドライバー別テストであり、テストを無効化したものではない。競合と一部のPostgreSQL専用経路まで検証する際は、別途許可された破棄可能なテストDBを使う。2026-11-07の最終検証では、既存DBと分離した新規の使い捨てコンテナーでこれらも実行した。結果と制限は[78の記録](78-final-quality-validation-2026-11-07.md)を参照。
- 認証契約: 実Firebase Web/Admin SDKとローカルAuthエミュレーターで、同じUIDのGoogle連携・パスワード設定・再認証・解除を検証。実GoogleのOAuth画面やクラウド上のアカウントは操作しない。
- 型・Lint・テスト・ビルドは画面の見た目までは保証しない。UI変更では共通仕様に従い、変更箇所と影響する操作をPC1280px・スマートフォン390pxで確認する。共有レイアウト・レスポンシブ挙動を変更する場合はタブレット768pxと該当する境界幅も確認する。変更しない画面や操作を毎回一巡する必要はない。新たなブラウザーE2Eフレームワークは今回追加していない。

## CI

`.github/workflows/refactor-check.yml`でpush・pull request・手動起動を対象に、Node.js 22の最新版／`npm ci`／`verify`／`build-storybook`／`test:auth`を実行する。権限はcontents: read、上限20分。同じブランチの古い実行を取り消す。GitHub Secretsや実環境のFirebase変数を要求せず、デプロイ処理は含めない。

## 失敗時の対応

| 症状 | 対応 |
| --- | --- |
| 型チェックでルート型がない | `typecheck`を使用する。直接の`tsc`だけでは初回のNext.js型生成を行わない |
| Lintが警告で失敗 | 警告も修正する。上限やルールを緩めて成功扱いにしない |
| DBテストのメモリー不足 | `test:db`の直列実行を使用する。全ファイルを無制限に並列実行しない |
| エミュレーターのポート競合 | 9099・4400・4500番ポートを確認する。既存サービスを勝手に停止せず、競合を解消して再実行する |
| サンドボックスでローカルポートがタイムアウト／EACCES | 製品コードを変えず、ローカル接続を許可された環境で同じコマンドを再実行する |
| 実PostgreSQLのテストがskip | PGliteの範囲を確認する。実DBの初期化を自動で実行して埋め合わせない |

実行結果・調査記録は[70. 自律開発の検証環境整備](70-autonomous-validation-2026-11-03.md)を参照。
