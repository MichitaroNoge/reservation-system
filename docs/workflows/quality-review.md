# 品質レビュー

[手順書一覧へ戻る](README.md)

確認日: 2026-11-08。変更の目的、既存仕様への影響、検証結果を確認し、PRを取り込める状態か判断する手順です。自動レビューの指摘が0件でも、未確認事項がなくなるわけではありません。

## 1. 対象と判断基準を決める

1. 対象チャット・Worktreeのパス・ブランチ・HEAD・未コミット差分を確認する。PRがあればURLと最新コミットも記録する。
2. 最新の依頼、[AGENTS.md](../../AGENTS.md)、[標準仕様](../standard-specification.md)、[関連仕様の一覧](../README.md)を読む。未承認の提案を合格条件に追加しない。
3. 顧客画面は[顧客画面の共通仕様](../customer-screen-standard.md)、UIは[デザインシステム](../ui-design-system.md)も使う。
4. 対象外ファイルの変更や、依頼していないDB・依存パッケージの更新が混ざっていないか確認する。文書だけの変更ならアプリコードが変わっていないことを確認する。

## 2. CodexとGUIで差分を読む

1. Codexのレビューペインで、未コミット変更またはmainとの差分を確認する。どの範囲の差分かを明示し、最新の1操作分だけで全変更を見たと判断しない。
2. 入力欄で`/review`を使い、未コミットなら`Review uncommitted changes`、ブランチの変更なら`Review against a base branch`でmainを選ぶ。手元の版で表示が異なる場合は要確認として、通常のチャットで対象と条件を明記してレビューを依頼する。
3. 指摘ごとに対象ファイル・再現条件・利用者への影響・根拠を確認する。自動修正が必要なら別途修正を依頼し、差分と検証を再確認する。
4. GitHub Desktopの`Changes`、PRの`Files changed`でも対象範囲を読む。既存の別作業を今回の変更と取り違えない。

Codexのレビュー範囲と`/review`は[OpenAI公式文書](https://learn.chatgpt.com/docs/code-review)参照。

依頼例:

```text
このWorktreeの未コミット変更を、最新の依頼・AGENTS.md・標準仕様・関連仕様と照合してレビューしてください。
まずパス・HEAD・差分の範囲を確認してください。
既存の業務ルール、API、認可、エラー・再試行・競合時の挙動への影響を確認し、
具体的な不具合を優先度、再現条件、対象ファイル、根拠とともに報告してください。
仕様上の提案と確定要件を区別し、未確認事項も列挙してください。この依頼ではコードを修正しないでください。
```

## 3. ローカル検証を行う

各コマンドは対象Worktreeのルートで実行します。Codexに依頼して実行させても構いません。Node.js 22以上とnpmを確認し、新しいWorktreeでは先に`npm ci`を行います。

```powershell
npm run verify
npm run test:auth
```

| 検証 | 実行される内容と注意点 |
| --- | --- |
| `verify` | `typecheck` → `lint` → `npm test` → `test:db` → `build:check`。途中で失敗したら以降は未実施 |
| `typecheck` | Next.jsのルート型生成後にTypeScriptの型チェック |
| `lint` | 警告0件を要求。ルールや上限を緩めて成功扱いにしない |
| `npm test` | 通常の単体・回帰テスト。成功件数だけでなく失敗・skip・終了コードを見る |
| `test:db` | 独立した一時PGliteで実行。実PostgreSQL専用のテストはskipされるため、その範囲は未検証として区別 |
| `build:check` | 検証用のダミー設定で`npm run build`を呼び、`.next-check`へ出力。配布用の生成物にはしない |
| `test:auth` | ローカルのdemo Authエミュレーターで実SDKの契約テスト。9099・4400・4500番を使用し、終了後に停止を確認 |

根拠は[package.json](../../package.json)、[検証スクリプト](../../scripts/validate.ts)、[既存の検証手順](../validation.md)です。AGENTS.mdの`npm test`・`npm run build`は`verify`内で実行されることをログでも確認します。通常の`npm run build`を別途実行する場合は環境設定を使用して`.next`へ出力するため、検証用の`build:check`と区別します。

通常検証は実DB・実メール・実OAuthの認証情報を使わない構成です。`dev:local` / `start:local`はアプリとワーカーを起動するためテストの代用にしません。実PostgreSQL検証は専用DBを初期化する別工程であり、skipを埋めるために既存DBへ実行しないでください。必要なら接続先と破棄可能性を確認し、[validation.md](../validation.md)の手順に従います。

2並列では`test:auth`を順番に実行します。ポートが使われている場合は他のテストやサービスを調べ、共有プロセスを勝手に停止しません。

## 4. 変更に応じた確認を加える

| 変更対象 | 確認する内容 |
| --- | --- |
| 顧客・管理画面 | 重要操作をPC1280px、タブレット768px、スマートフォン390pxで確認。入力ラベル・エラー・読み込み・空・成功・無効状態、横スクロール、戻る操作、キーボード操作を確認 |
| 予約・人数・店舗割当 | 変更対象の受付条件・状態遷移と、不正入力や古い状態での拒否。詳細条件は対象機能の仕様と既存テストで確認 |
| 認証・権限 | 未ログイン・他人のデータ・権限不足・失効時の拒否。UI非表示だけでなくサーバーの判定を確認。重要な仕様変更は承認対象 |
| DB・メール・カレンダー | 保存失敗、重複実行、再試行、競合、外部連携失敗時の挙動。架空データと隔離環境で確認し、実宛先へ送って検証しない |
| Markdown | 相対リンク、ファイル名、コマンド名、チェックリスト、AGENTS.mdとの整合性、確認済み／要確認の区別。GUIの未確認操作を断定していないか確認 |

画面の表示幅や隔離検証の基準は[validation.md](../validation.md)に従います。画面変更がなければ画面確認を「対象外（画面変更なし）」と記録します。HTTPテストの成功を、実画面や実Google OAuthの操作成功として報告しないでください。

## 5. 失敗・指摘を扱う

1. エラーの段階・再現条件・ログ・対象コミットを記録する。既存不具合か、今回の差分か、実行環境の制約かを調査する。
2. 安全に修正できる範囲を修正し、失敗した確認と必要な回帰検証をやり直す。指摘を消すためにテストを無効化しない。
3. 同じ問題で3回失敗した場合はAGENTS.mdに従って方針を再検討する。未解決なら理由と影響を報告する。
4. 再検証していない変更がある状態で、古い成功結果を最新結果として扱わない。

## 6. CIとマージ前の確認

1. GitHubのPRで最新コミットのChecksを開く。ローカルの成功とGitHub Actionsの成功を別々に確認する。
2. 現在の[Refactor Check](../../.github/workflows/refactor-check.yml)はNode.js 22で`npm ci`、`verify`、`test:auth`を実行する。必須Checkとして保護ルールに登録されているかは要確認。
3. 失敗時はログを読み、キャンセルされた古い実行を成功扱いにしない。同じブランチの古いCIが自動キャンセルされる設定がある。
4. mainが更新されたら作業ブランチへ取り込み、統合結果を再検証する。[2並列開発](parallel-development.md)の順序に従う。
5. レビュー指摘・未確認事項・本番自動反映の有無・マージ依頼の範囲を確認する。必須条件を迂回してマージしない。

## 結果の記録例

```markdown
- 対象: チャット名 / Worktreeパス / ブランチ / HEAD / PR URL
- 変更: 問題と変更後の動作
- 仕様: 確認した文書と、今回の依頼との関係
- 検証: コマンド / 日時 / 終了コード / 件数・skip / 対象コミット
- 画面: 幅 / 確認操作 / 結果、または対象外の理由
- CI: 最新コミットの実行結果
- 指摘: 修正済み / 未修正と影響 / 再検証結果
- 未確認: 環境制約、実PostgreSQL限定経路、実OAuth等
- 反映: ローカルのみ / Push済み / PR作成済み / mainへマージ済み
- 本番: デプロイの実施有無（mainマージと区別）
```

## チェックリスト

- [ ] 対象パス・HEAD・レビュー範囲を確認した
- [ ] 最新の依頼と確定仕様を照合した
- [ ] 不要な変更・秘密情報・個人情報がない
- [ ] 型チェック・警告0件のLint・通常テスト・DBテスト・ビルド結果を確認した
- [ ] Authテストの結果とエミュレーター停止を確認した
- [ ] 影響する正常・拒否・失敗・再試行・競合の確認を行った
- [ ] UIのPC・モバイル確認を行った、または対象外の理由を記録した
- [ ] 指摘修正後と最新main取り込み後の再検証を行った
- [ ] 最新コミットのCIとレビュー条件を確認した
- [ ] skip・未実施・未解決事項と反映状況を報告した

## 要確認

必須レビュー人数、承認者、必須Checks、署名やマージ方式の強制、外部デプロイ設定はローカルのコードだけでは確定できません。[一覧の要確認事項](README.md)を参照してください。自動レビューの利用可否や画面上の配置も、使用中のCodexの版と権限で確認してください。
