[手順書一覧へ戻る](README.md)

## 1. 整理する対象を分ける

| 対象 | 整理したときの意味 |
| --- | --- |
| Codexのチャット | 会話の整理。アーカイブはPRのマージではない |
| Codex管理のWorktree | 作業フォルダーの整理。GitHubのブランチ削除とは別 |
| ローカルブランチ | ローカルの履歴の名前を削除する操作 |
| GitHub上のブランチ | リモートのブランチを削除する操作。ローカルの変更が保存されるわけではない |
| DB・コンテナー・Volume | Worktreeとは別の資源。Worktreeの整理を理由に初期化・削除しない |

## 2. 片付け前の保存確認

1. PR URLと対象Worktreeの実パスを確認する。作業A・Bを別々に確認し、名前だけで削除対象を判断しない。
2. GitHubのPRが`Merged`で、意図した変更がmainに存在することを確認する。`Closed`だけでは不十分。統合後の検証が失敗している場合は整理を保留する。
3. GitHub DesktopでそのWorktreeを選び、`Changes`と`History`を確認する。未コミット差分やPRへ含めていないコミットがあれば、その保存方針を先に決める。
4. Codexに、対象パスを指定してGit状態・追跡先との差・Git管理外ファイルの有無を読み取り専用で確認させる。上流ブランチがない場合も「未Pushなし」と判断しない。
5. メモ、画像、`.env.local`等はGit管理外の場合がある。必要なものを管理されたローカルの保存先に退避し、内容を再確認する。秘密情報をPRへ添付して保存しない。
6. Squash / Rebaseでマージした場合はコミットSHAが変わり得る。単に「mainに元のSHAがない」だけで未マージと判断せず、PRのMerged表示と実際の変更内容を確認する。

確認を依頼する例:

```text
このチャットのWorktreeを整理する前の確認だけをしてください。
絶対パス、ブランチ、HEAD、未コミット変更、未追跡ファイル、
追跡先と未Pushコミットの有無、Git管理外の保存が必要なファイルの有無を確認してください。
秘密情報の中身は表示しないでください。PRのマージ結果とmainへの反映も確認してください。
まだアーカイブ・削除・変更の破棄・DB操作はしないでください。
```

## 3. 自分が起動したプロセスを停止する

1. 対象Worktreeのアプリ、テスト、開発サーバー、ワーカー等が動いていないか確認する。
2. 自分が起動したターミナルで`Ctrl+C`を使って終了する。共有プロセスか不明な場合は停止せず確認する。
3. `dev:local` / `start:local`はメール・カレンダーワーカーも扱うため、終了ログを確認する。[ルートREADME](../../README.md)参照。
4. ファイル使用中エラーがある場合は対象を調査する。全Nodeプロセスの強制終了やPC全体への一括削除をしない。

## 4. Codex管理のWorktreeを整理する

Codex管理のWorktreeは、Codex側の管理操作を優先します。公式文書では、関連チャットのアーカイブによるWorktreeの自動整理と、保存されたスナップショットからの復元が説明されています。ただし、これを唯一のバックアップにはしません。[OpenAI公式文書](https://learn.chatgpt.com/docs/environments/git-worktrees)参照。

1. 保存と停止の確認後、Codexで整理対象のチャットを開き、パス・ブランチ・PRを再確認する。
2. 対象チャットのアーカイブ操作を行う。手元の版でのメニュー位置・日本語表示は要確認。操作が見当たらない場合は、対象を明記してCodexに「保存確認済みのこのチャットに付属する管理Worktreeをアーカイブしてください」と依頼する。実際のチャットのアーカイブとWorktreeのアーカイブは結果を分けて確認する。
3. 完了後、対象のWorktreeが有効な作業先から外れたこと、元のチェックアウトともう一方の作業が残っていることを確認する。確認できない場合は「整理済み」と記録しない。
4. 復元が必要ならアーカイブ済みのチャットを開き、表示された復元操作を確認する。表示されない場合は対象チャットからCodexに管理Worktreeの復元可否を確認する。具体的なGUI配置、スナップショットの保持期間・保持対象は要確認。

Codexの管理フォルダーをエクスプローラーから直接削除したり、GitHub DesktopのWorktree削除機能と重ねて使用したりしないでください。GitHub Desktopにも削除機能はありますが、この手順ではCodex管理の対象はCodexで整理します。削除エラー時に強制削除へ進めないことも含め、[GitHubのWorktree管理の説明](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-worktrees-in-github-desktop)を参照できます。

## 5. ブランチを整理する

1. PRがMergedで、追加作業・他のPR・他のWorktreeが使っていないことを確認する。削除の依頼範囲を確認し、対象名を再確認する。mainは削除しない。
2. GitHub上のブランチは、マージ済みPR画面で`Delete branch`が利用できる場合に削除する。既に自動削除されている場合は重複操作しない。リモートの変更操作なので、承認範囲を確認して行う。[PRマージ後の整理](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request)参照。
3. ローカルブランチは、Worktree整理後、元のチェックアウトに未コミット変更がないことを確認してから、GitHub Desktopで対象ブランチを選び、`Branch` → `Delete...`を使用する。確認画面に追加の削除対象があれば内容を読む。使用中・未マージ等の警告が出たら中止し、状況を調査する。[公式手順](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-branches-in-github-desktop?platform=windows)参照。
4. 元のチェックアウトでmainへ戻り、Fetch・Pullする。対象のブランチやWorktreeが意図どおり整理され、必要な作業が残っていることを確認する。

ブランチを残しておいても、マージ済みの変更はmainから利用できます。削除条件が曖昧なら残し、理由を記録してください。
